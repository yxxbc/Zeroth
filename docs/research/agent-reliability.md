# Zeroth Agent 可靠性与效果工程设计

日期：2026-11-17

状态：设计提案。本文定义后续实现目标，不表示这些能力已经交付。
本文新增的数据结构、记录类型、目录与命令均为拟议接口；现有能力在第二节单独列出。

## 1. 目标与适用范围

Zeroth 要让用户能够把多步骤编码任务交给 Agent，在中断后继续工作，定位失败原因，
并通过可重复的任务评估判断系统修改是否改善了实际效果。

本文吸收 AgentSphere 职责描述中的可靠执行、上下文工程、执行内核和评估闭环，
将其落实到 Zeroth 的终端编码 Agent、headless 和子 Agent 场景。
招聘描述只提供设计启发，不能作为对方实现方式或生产效果的证据。

交付目标如下：

| 编号 | 目标 | 用户能够观察到的结果 |
| --- | --- | --- |
| G1 | 任务中断后恢复目标、约束、进度和执行证据 | 重启后知道已经做了什么、哪些结果需要核对、接下来可以做什么 |
| G2 | 对工具执行提供可追踪的生命周期与恢复决策 | 已完成操作不因重启被自动重做，结果未知的调用被明确列出 |
| G3 | 建立固定任务集及候选版本比较流程 | 每次提示词、工具、compact 和执行策略修改都有质量、耗时及用量报告 |
| G4 | 在上下文压缩和恢复时保留有效约束及任务状态 | 长会话继续遵守用户要求，文件和测试证据不会被摘要误写成已验证事实 |
| G5 | 统一各入口的执行协议 | 交互模式、headless、子 Agent 对相同执行条件给出一致的结果分类 |

范围覆盖单机工作区内的任务、模型请求、工具执行、任务状态和评估产物。
公司级资产注册、租户管理、远程运行实例迁移和跨机器进程接管另需专门设计。
本文不对这些场景作出交付承诺。

## 3. 总体结构与标识

执行事实沿以下路径流动：

```text
用户目标与约束
    -> TaskState + ContextManifest
    -> run_agent 执行协议
    -> 权限与 hooks -> 执行日志屏障 -> ToolExecutor
    -> 工具结果与验证证据 -> 执行终态记录
    -> Session / rollout / UI / headless
    -> 评估报告与失败案例
```

执行事实由边界产生，状态转换和恢复决策由纯函数计算。
UI 负责显示，模型负责提出计划与调用，二者都不能将没有证据的执行改写为成功。

### 3.1 标识定义

| 字段 | 含义与稳定性 |
| --- | --- |
| session_id | 对话标识，跨正常恢复保持不变 |
| task_id | 现有任务标识，在 session_id 范围内唯一；模型未建清单时使用持久化的根任务标识 |
| run_id | 一次运行实例，重启、恢复或评估重跑生成新值 |
| turn_id | 一次用户回合，跨该回合的模型重试保持不变 |
| request_id | 一次实际模型请求，由 Zeroth 分配；服务端标识另存 provider_request_id |
| operation_id | 一次逻辑工具操作，重试或核对时用于关联；不能仅用参数摘要去重 |
| attempt_id | 操作的一次执行尝试，只有新执行才生成 |
| event_seq | 会话执行日志的单调递增序号，用于排序、去重和快照截点 |
| context_revision | 结构化任务上下文的版本 |
| policy_fingerprint | 当前工具、权限及相关配置的摘要，不含凭证 |

同一命令可能被用户合法执行多次，不能因为工具名和参数相同就判为重复操作。
重试由显式关系关联前一次 operation_id；无关联的新调用具有新的 operation_id。

### 3.2 存储职责

Rollout 继续承担完整对话和已有工具结果的记录。新增会话执行日志保存执行意图、
状态变迁、证据引用和任务上下文修订；两者通过标识关联，不复制流式输出。
执行日志与 rollout 放在同一个会话存储根目录，通过 session_id 找到对应关系。

执行日志是恢复决策的事实来源，rollout 是对话和展示的事实来源。
二者分别写入，不假设跨文件原子提交。执行终态已落盘而 rollout 尚未写入时，
恢复器按 operation_id 补齐可重建的结果；已有结果不再重复插入。
Rollout 已有历史结果但缺少执行日志的旧会话，不推断它曾经过新的持久化协议。

终态记录必须包含重建模型工具结果所需的状态、错误类别和结果文本，或引用已先行同步的
不可变结果产物。长输出先流式写入独立产物，完成同步及校验摘要后才能提交引用它的终态；
尚被有效终态引用的产物不得被清理。产物丢失或校验失败时保留已知执行状态，报告
result_unavailable 并阻止依赖该结果的自动续做，不能伪造输出或通过重跑副作用补造结果。

任务状态快照记录最后应用的 event_seq，由临时文件写入、同步并原子替换生成。
快照只是加速读取的派生产物，损坏后可以从有效执行日志重建。
文件中间损坏不能当作正常尾部截断跳过；恢复器停止执行并报告损坏位置。

## 4. 任务恢复与执行可靠性

### 4.1 目标行为

用户在多步骤任务中退出或遭遇进程崩溃后，重新进入会话能够看到：任务目标、有效约束、
任务清单、最近验证结果、未决操作、工作区变化，以及可执行的继续方案。

恢复读取状态不启动工具、不重放旧命令，也不自动覆盖工作区。
用户发出继续指令后，只执行恢复计划允许的步骤，并重新应用当前权限和 hooks。
既有回退入口保持其已定义的文件恢复语义；“崩溃续做”是单独的恢复路径，界面上明确区分。

### 4.2 工具操作状态

| 状态 | 含义 | 恢复时的处理 |
| --- | --- | --- |
| proposed | 模型提出调用，尚未获准执行 | 按当前策略重新评估，不继承旧批准 |
| rejected | 权限或 hook 拒绝，工具没有启动 | 保留拒绝原因，不自动重试 |
| prepared | 最终参数与执行意图已持久化，可能尚未启动 | 视为结果未知，先核对；不能据此断言没有执行 |
| running | 已观察到启动，尚无终态 | 核对结果与资源状态，不直接重跑 |
| succeeded | 有持久化成功结果 | 复用结果；继续依赖它前检查证据是否仍有效 |
| failed | 有持久化失败结果 | 保留错误类别；失败可能已有副作用，按操作策略决定重试 |
| cancelled | 已确认本次尝试停止，并记录已知结果 | 保留已发生的副作用，不将取消等同于回滚 |
| unknown | 启动或结束情况无法确认 | 执行只读核对；仍不能确认时标记需人工处理 |

每个 attempt_id 只有一个不可变执行终态。崩溃恢复产生的 unknown 是对未决尝试的判断，
后续核对以独立 resolution 记录补充结论，不伪造原执行过程。
重试创建新的 attempt_id，之前的记录保持可见。

### 4.3 持久化顺序与故障窗口

工具调用依次经过：参数解析、权限判定、hook 处理、最终参数授权校验、prepared 记录、
持久化屏障、实际执行、终态记录、持久化屏障、向模型和会话交付结果。
Hook 修改参数后，实际执行参数必须仍受有效授权覆盖；否则重新走既有授权流程。

开始执行前必须确认 prepared 及其依赖的目标和约束修订已同步到磁盘。
副作用完成后必须确认终态同步成功，才能把它作为持久化成功交给后续步骤。
同步等待放在工作线程中，由有界队列连接事件循环，不能阻塞终端输入与取消。
磁盘满或写入失败时停止派发新操作，向用户报告持久化失败。

```text
prepared 已同步 -> 工具产生副作用 -> succeeded 已同步
                       ^
             此处崩溃：结果未知，进入核对
```

本地日志不能使任意外部系统提供 exactly-once 执行保证。
文件日志屏障解决“执行前没有意图记录”，结果核对解决“操作做了但结果没记下来”。
支持幂等键的外部接口才能进一步利用稳定的操作标识防止重复提交。
断电后的持久性以操作系统、文件系统及同步调用的保证为边界，不能由进程测试外推。

### 4.4 操作分类与核对策略

分类由内置工具契约或可信工具声明提供；模型文字、命令前缀匹配和 MCP 描述文本
均不能把任意操作升级为可自动重试。未知工具和任意 shell 默认归入 unknown_effect。

| 分类 | 例子 | 自动恢复条件 |
| --- | --- | --- |
| read_only | 已声明的本地读取 | 重新校验权限后允许读取；结果注明读取时间 |
| guarded_local_write | 带前置内容摘要的结构化 edit/write | 核对目标内容是否为预期结果；原内容仍匹配时可创建新尝试 |
| idempotent_external | 接口提供幂等键和结果查询 | 以相同幂等键查询或重试，并记录外部结果标识 |
| unknown_effect | 任意 shell、未知 MCP、无幂等契约的外部调用 | 不自动重跑；提供核对结果和需要用户判断的具体问题 |

结构化文件写入还需区分创建、覆盖、删除和多文件修改，记录前后内容摘要、路径及
实际完成情况。多文件操作只完成一部分时逐文件报告，不标记整体成功。
文件检查点不能撤销网络请求、数据库写入或其他外部副作用。

典型案例：提交命令结束前进程崩溃。恢复器核对仓库当前提交、预期父提交和差异，
证据充分时标记已完成；状态不同或不能确定时停止该步骤，不能直接再执行提交命令。
针对该场景的核对器只执行明确实现的只读查询，不执行记录里的任意核对脚本。

### 4.5 工作区、后台进程和子 Agent

恢复计划绑定工作区规范路径、检查点标识、相关文件摘要和 context_revision。
执行前重新验证；用户在查看计划后改动文件，则计划失效并重新计算。
工作区发生变化时保留当前文件，将相关验证证据标记为 stale，列出需要重读和重验的步骤。

后台任务持久化逻辑标识、启动信息和输出位置。PID 不是身份凭证，不能据此接管或终止进程。
只有能够验证进程身份、所有权和通信通道时才允许重新附着；其他情况标记 detached_unknown，
不向可能被复用的 PID 发信号，也不自动启动替代进程。

子 Agent 记录父任务、运行标识和结果证据。父进程重启后不能凭旧进度文字判定子任务完成。
已有持久化结果可复用，未决运行进入核对；需要重启的子任务获得新的 run_id。

### 4.6 兼容与验收

旧 rollout 可以继续阅读和按既有语义恢复，界面注明没有执行恢复证据。
旧任务清单保留其快照及编号；不从自然语言补造执行成功记录。
执行日志使用独立 schema_version。未知的执行控制记录必须阻止自动续做，不能静默跳过。
截断尾行可隔离后恢复到上一个完整事件，并保留原文件以供诊断。

验收必须覆盖：执行前退出、prepared 后退出、副作用后退出、终态后退出、rollout 写入前退出、
磁盘写满、重复事件、尾部截断、中间损坏、双进程竞争、工作区外部改动、PID 复用、
结果产物丢失和超时后副作用才完成。
同一会话只有持有排他写锁的实例能够执行；其他实例只能读取或报告占用。
上述所有故障注入场景中，不得自动重做 unknown_effect 操作，不得丢失已同步的成功终态。

## 5. 效果评估与回归闭环

### 5.1 评估目标与任务集

评估回答四个问题：任务是否完成、约束是否满足、付出多少执行成本、失败发生在哪个阶段。
进程退出成功和模型声称完成都不能代替任务完成判定。

首批交付固定 30 个任务，每类 5 个，案例及其验证器进入版本管理：

| 类别 | 任务内容 | 主要验证方式 |
| --- | --- | --- |
| 故障修复 | 根据失败测试定位并修复缺陷 | 外部验证器运行回归测试并检查修改范围 |
| 功能实现 | 在现有工程中完成带约束的功能 | 验收测试、公开接口检查和文件差异 |
| 长上下文 | 多轮补充、纠正和 compact 后继续编码 | 检查有效约束与关键事实是否保留 |
| 中断恢复 | 在指定执行窗口终止并重启 | 核对恢复状态、文件和外部副作用次数 |
| 工具故障 | 超时、拒绝、输出截断及工具错误 | 任务结果、错误分类及后续行为 |
| 入口一致性 | 相同脚本事件用于交互、headless 和子 Agent | 比较公共执行事件及权限边界 |

每个案例包含：case_id、数据集版本、required_capabilities、activation_stage、初始工作区、用户输入序列、模型配置、工具策略、
网络策略、预算、故障注入点、验证器、预期产物，以及约束检查条件。
案例数据使用可公开分发的 fixture，不直接收录私人会话、密钥或用户源码。

### 5.2 三种运行类型

1. **协议回归**：使用 dummy 或脚本化模型及工具，离线执行，验证恢复状态机、上下文构造和入口契约。
2. **真实任务评估**：真实模型在独立工作区执行，用外部验证器判定结果；显式触发，运行前展示预算。
3. **事件重放分析**：读取已有 rollout 和执行日志计算指标或重建界面，不执行日志中的工具。

三种报告分别标识运行类型。离线脚本通过只能证明执行协议成立，不能证明真实模型的任务能力。
读取记录进行重放也不等于重新运行同一任务。

### 5.3 运行隔离与可重复性

每次运行使用独立工作区、配置目录、会话目录、检查点、scratchpad 和任务输出目录。
Hooks、MCP、技能和项目配置由案例显式提供，不读取操作者个人配置。
工作目录隔离不等于安全沙箱；需要限制文件和网络访问的案例必须使用具备相应强制边界的运行环境。
Runner 记录实际隔离能力，不满足案例要求时拒绝启动，不能声称已隔离后继续执行。

验证器及测试预期保存在 Agent 无法修改的位置，避免通过改测试伪造完成。
验证在任务执行结束、子进程完成清理后运行，持有自己的超时与结果文件。
联网案例记录网络依赖、时间和响应 fixture 策略；依赖不可用时标记 infrastructure_error。

预算分别限制模型请求数、工具调用数、墙钟时间、并发任务数及 token 用量。
费用只在存在明确的带版本价格表时估算，并标注币种与价格日期；否则只报告用量。
调用前检查已知余额及请求预留量，调用后按实际用量核销。服务端报告延迟和在途请求
可能造成超出预留，报告必须保留超额事实，不能承诺无法强制的费用硬上限。

### 5.4 指标与结果状态

| 指标 | 定义 |
| --- | --- |
| task_success | 外部任务验证器通过，且强制约束全部满足 |
| constraint_violation | 按约束标识记录被违反的要求及证据 |
| duration_ms | 从任务启动到收尾清理完成的单调时钟耗时，另报验证耗时 |
| model_usage | 每请求 input、output、cached、cache_write、reasoning，缺失值标为 unavailable |
| tool_failures | 按既有错误分类聚合，区分实际执行失败与未执行的拒绝 |
| recovery_outcome | 已完成复用、核对后继续、等待人工判断或恢复失败 |
| duplicate_side_effects | 验证器观测到的非预期重复副作用次数 |
| evidence_staleness | 继续执行前发现失效的文件或测试证据数 |

运行结果区分 passed、failed、budget_exceeded、cancelled、infrastructure_error 和 invalid。
超时及预算耗尽计入未完成任务；基础设施错误独立报告，不能从总数中悄悄删除。
子 Agent 用量归入父任务总计，同时保留分项；汇总不得重复计费。
缺失用量不能当作零，成本不完整的报告不能参与完整成本指标的优劣结论。

### 5.5 候选比较与发布判定

真实模型比较使用相同案例、输入、模型设置和工具策略，每个案例运行 3 次，
基线与候选分别产生 90 个结果。按案例配对报告成功变化、耗时中位数和分位数、
token 分项及每次失败证据。模型本身是比较变量时，其他设置保持一致并记录差异。
报告注明重复运行不能消除服务端模型变化；支持固定模型版本时记录该版本。

已激活能力的协议回归必须全部通过，重复副作用、越权调用和终态丢失的确定性案例必须为零。
真实任务评估出现任一强制约束违规，候选进入阻断状态；新失败案例必须逐条审阅。
其余质量和性能阈值保存在带版本的 gate 配置中，运行前读取并写入报告，
不能看到结果后调整阈值再宣称通过。未配置阈值时输出 comparison_only，不输出通过结论。
成功率同时报告样本量与不确定性，不能以单次运行或微小分差宣称能力提升。

### 5.6 报告、命令与失败案例回流

拟议命令如下，当前尚未实现：

```text
zeroth eval run --suite coding --mode scripted --output <directory>
zeroth eval run --suite coding --mode live --budget <file> --output <directory>
zeroth eval compare <baseline-directory> <candidate-directory> --gate <file>
```

命令输出机器可读结果及 Markdown 报告，包含运行配置、二进制及提示词指纹、数据集版本、
有效 gate、逐例结果、完整性标记和产物索引。脚本回归不触发真实模型请求。
真实任务评估必须显式选择 live，凭证通过运行环境注入，报告不保存凭证。

失败案例处理流程为：定位失败阶段、提取可分发 fixture、编写能判定该故障的验证器、
复现当前错误、修复、纳入任务集并更新数据集版本。真实会话只在经过审阅和脱敏后用于构造 fixture。
报告引用完整输出文件和摘要，不把所有日志加载为一个内存对象。

### 5.7 验收标准

30 个案例均有独立验证器与说明，离线协议案例在无模型凭证、无个人配置的环境下可运行。
相同脚本输入重复执行产生相同的公共终态；时间和生成标识通过规范化后比较。
全部能力激活后，基线与候选的 90 次结果可以追溯到单次配置、执行日志、文件差异和验证输出。
人为注入一个质量回退、一个用量缺失、一个预算耗尽和一个基础设施失败，报告必须正确分类。
全部 live 运行由显式命令触发，常规单元测试、smoke 和协议回归不能暗中消耗模型额度。

## 6. 上下文状态与证据保留

### 6.1 任务上下文模型

上下文由完整历史、结构化任务状态和按预算选择的材料派生，完整历史继续保留。
新增 TaskState 与现有 TaskStore 关联，后者继续负责清单、依赖和编号。

| 字段 | 内容及更新规则 |
| --- | --- |
| objective | 当前目标及对应用户消息位置；目标变更生成修订 |
| constraints | 带来源、作用域、有效状态及替代关系的要求 |
| progress | 对现有 task_id 的引用、完成声明和验证状态 |
| evidence | 文件摘要、命令结果、验证器结果及其适用条件 |
| blockers | 阻塞原因、来源与解除条件 |
| next_actions | 候选后续步骤，仅表示计划，不代表已获执行授权 |
| unresolved_operations | 执行日志中的未决操作引用 |

Constraint 至少包含标识、原始要求、来源消息、适用范围、创建修订及替代关系。
模型可提议提取约束，但提取结果不能提高来源的权限，也不能改写用户的原话。
明确的用户纠正替代对应旧要求，旧条目保留为 superseded；无法判断是否替代时保留冲突，
显示两条原文并请求澄清，不让摘要自行选择。所有约束仍遵循既有指令优先级和授权规则。
工具输出、仓库文件和检索材料保留数据来源属性，不能转为高优先级指令。

完成状态区分 reported 和 verified。模型将任务标为完成只产生 reported；
只有匹配验收条件的验证证据才产生 verified。没有机器验证器的任务保留完成声明来源，
不能为了状态好看伪造验证结论。

### 6.2 证据有效性

文件证据绑定路径、内容摘要和读取时间；代码验证绑定执行命令、退出码、工作区摘要和运行环境。
工作区相关内容变化后，依赖旧内容的证据标记 stale；历史成功依旧是历史事实，
但不能据此宣称当前代码仍通过验证。外部证据还需记录资源标识和查询时间。

恢复和 compact 只保存证据引用及摘要，不将原始长日志反复注入模型。
需要复核时按引用读取对应片段；引用不存在、文件已变化或输出截断时明确报告。
摘要不能把“准备测试”“运行中”“测试失败”改写成“测试通过”。

### 6.3 上下文装配与预算

预算按以下顺序分配：有效指令和用户要求、目标及未决操作、任务进度和关键证据、
当前相关源码与工具结果、历史摘要及补充材料。模型输出空间、工具 schema 和协议封装
一并计入窗口预留，不能只计算对话文本。

所有有效强制约束必须在上下文中得到保留，不允许静默裁掉。
如果这些内容连同协议和输出预留已经超过可用窗口，则暂停新的任务执行，
报告冲突预算，要求缩小当前任务范围或选择可容纳的模型；不能假装装配成功。
可重新取得的源码和日志以路径、范围、摘要和内容指纹替代重复全文。
预算计算复用现有 token 估算机制，记录估算值及服务端实际用量的差异。

每次装配生成 ContextManifest，列出 context_revision、材料来源、选入和省略原因、
各部分估算用量及失效证据。调试视图基于相同 manifest 展示，避免看到的内容与请求不一致。

### 6.4 compact、恢复与回退

compact 开始时固定 history 截点与 context_revision，基于该版本生成叙述摘要。
有效约束、TaskStore 和执行事实从结构化状态派生，不能让摘要模型重写它们。
完成后检查来源引用、有效约束覆盖和未决操作覆盖；不满足要求则拒绝应用该摘要。
生成期间若上下文版本变化，丢弃候选并保留原状态，不能将旧摘要覆盖新要求。

compact 继续沿用追加标记及派生上下文的设计，不重写历史或改变检查点编号。
恢复时从持久化修订重建 TaskState；回退时按历史分支和 event_seq 恢复相应版本，
旧分支执行事实保留审计记录，但不能继续作为新分支的有效完成证据。
任务清单全部完成后仍可按现有规则从界面退休，证据和归档记录保留。

### 6.5 验收标准

测试覆盖连续 5 次 compact、用户替换要求、来源冲突、摘要遗漏约束、空摘要、
摘要期间修订变化、恢复旧会话、回退后继续、文件外部修改及强制约束超预算。
所有测试中，有效强制约束覆盖率为 100%，无证据的完成声明不得升级为 verified。
对同一历史截点、结构化状态和预算，装配过程给出相同的材料选择及 manifest。
通过真实任务评估单独验证约束保留对任务结果的影响，不从结构测试推断模型一定遵守要求。

## 7. 执行内核与入口契约

### 7.1 职责边界

| 层 | 负责内容 | 接入点 |
| --- | --- | --- |
| 纯状态与决策 | 操作转换、恢复计划、上下文装配、预算及证据失效 | 现有 app、context、tasks 及新增纯模块 |
| Agent 执行协议 | 模型请求、工具派发、取消、重试、事件关联及终态 | 现有 llm::agent::run_agent |
| 工具与持久化边界 | 文件、进程、MCP、执行日志写入及持久化屏障 | 现有 ToolExecutor 和记录器边界 |
| Session 与入口适配 | 用户输入、steer、queue、权限交互和事件折叠 | 现有 Session、TUI 与 headless |
| 展示与报告 | 转录、进度、恢复说明、JSON 和评估报告 | UI、headless 输出及评估 runner |

执行协议从现有代码逐项提取规则并复用，不另建与 Session 行为漂移的 headless runner。
未来规划策略可以决定下一步调用，实际调用仍须通过同一权限、持久化、取消和结果协议。

### 7.2 公共事件与顺序

公共事件携带 session_id、run_id、turn_id，以及适用的 request_id、operation_id 和 attempt_id。
事件按语义覆盖：请求开始与结束、调用提出、授权结果、执行准备、执行开始、输出引用、
执行终态、用量、任务修订和回合终态。展示用流式 delta 不进入恢复日志。

授权拒绝不产生执行开始。真正启动的调用必须有 prepared；每次请求和执行尝试
在正常结束时均收敛到一个终态；崩溃留下的未决项交给恢复器核对。
重复投递的事件按事件标识幂等折叠。过期 run_id 的迟到输出保留诊断信息，不能修改当前运行状态。
当前工具批次的顺序执行与文本穿插保持原有契约，并发工具派发仍按独立设计处理。

### 7.3 取消、超时与清理

取消令牌覆盖模型请求、hooks、权限等待、工具执行和子 Agent。
取消后停止派发新操作，结束或分离现有资源，并记录每项清理结果。
只有确认停止的尝试才写 cancelled；无法确认的外部操作写为未决，不伪造清理成功。
预算耗尽使用单独的回合终止原因，不能混作用户取消。

超时首先结束本次等待或回合，并记录 timeout_observed，不直接证明工具已停止。
确认停止且结果为超时失败时提交 failed，使用既有 timed_out 错误分类；无法确认的操作
保留未决并进入 unknown 核对，后续完成通过 resolution 记录补充。未决操作未核对前不得重试。
终态归并采用一次提交规则：正常完成、已确认停止的取消和已确认的超时失败竞争时，
第一个被执行协议接纳的终态固定该尝试结果，其他事件成为诊断或核对记录，不能生成第二个终态。
截止时间使用单调时钟，记录时间使用墙钟。运行中的超时采用剩余预算传播，不能让每层重试重置总时限。

### 7.4 各入口差异与共同保证

交互入口可以显示现有权限对话；headless 无人可批准时按当前规则返回 approval_required；
子 Agent 继续受自身工具允许列表与父任务授权边界约束。
入口一致性意味着执行协议一致，不要求这些交互差异消失。

契约测试提供相同脚本模型、工具结果和授权决策，比较规范化公共事件及持久化结果，
排除渲染帧、时间和入口专属提示。另以专门案例验证无人批准、子 Agent 禁用工具、
steer 与队列等合法差异。
跨入口必须保证：无未授权执行、无漏记已执行调用、无重复终态、取消后无新派发、
父子用量不重复统计、后台资源归属可追溯。

## 8. 实施顺序与交付物

阶段按依赖推进，先建立可观察和可验证的事实，再增加执行恢复及上下文保证。
本节是实施计划，合入具体功能时仍需更新对应机制页和用户可见变更记录。

| 阶段 | 交付物 | 完成条件 |
| --- | --- | --- |
| A：评估与关联标识 | 标识定义、运行清单、评估 runner、30 个案例、报告与 gate 配置 | 离线协议回归可重复执行，显式 live 运行可生成完整比较报告 |
| B：执行事实与恢复 | 执行日志、写入屏障、排他写锁、恢复器、工作区核对和恢复展示 | 第四节故障矩阵通过，结果未知的有副作用操作不被自动重做 |
| C：任务上下文 | TaskState、约束修订、证据有效性、ContextManifest、compact 校验 | 第六节全部案例通过，长上下文 live 评估产生基线与候选报告 |
| D：入口契约收敛 | 公共事件、统一终态与预算传播、跨入口契约测试 | 第七节公共保证全部通过，入口差异有明确测试 |

案例依赖与激活阶段如下；复合案例取所需能力全部交付后的阶段：

| 能力 | 激活阶段 | 激活前的报告规则 |
| --- | --- | --- |
| 普通任务验证、现有工具结果与用量分析 | A | 使用现有 rollout；新增关联标识由 runner 清单映射 |
| 执行日志、故障注入后的核对与结果重建 | B | 对应案例为 pending_capability；执行日志字段为 unavailable |
| 结构化约束、证据失效与 ContextManifest | C | 对应案例为 pending_capability；上下文契约字段为 unavailable |
| 公共执行事件及跨入口契约 | D | 对应案例为 pending_capability；事件契约字段为 unavailable |

阶段 A 的完整报告要求所有 30 个案例均有定义、验证器、依赖和激活阶段，
已激活案例有全部执行结果，其他案例明确标记 pending_capability，不计为成功或执行失败。
报告分别列出总案例数、已激活数、已执行数及待实现数；通过结论只适用于已激活集合。
在能力全部激活之前，每个基线或候选执行已激活案例数乘以 3 次，不能宣称已完成全套 90 次评估。
现有 rollout、配置清单、文件差异和验证输出在 A 即为必需产物；执行日志从 B 起成为必需产物。
阶段 B、C、D 交付时逐一激活对应强制 gate。
对每次评估报告记录实际启用的能力与 gate 版本，避免阶段间分数不可比却被直接比较。

每个阶段交付包括：纯决策模块、边界实现、失败回归、机制文档、兼容说明和对应评估报告。
生产代码遵循 TDD，先看到针对目标行为的失败测试，再实现规则；终端边界按仓库 smoke 约定验证。

## 9. 验证与工程约束

当前变更仅新增设计文档及索引，不改变程序行为，不运行 Rust 构建和测试。
实现时按实际触及的区域取 AGENTS.md 验证矩阵的并集，完整测试留给 CI。

| 实现区域 | 必需验证 |
| --- | --- |
| 任务与纯状态 | 对应 app、tasks、context 和新增恢复状态机的定向测试 |
| Agent 执行与工具边界 | llm 定向测试及实际涉及的进程、后台任务、权限测试 |
| TUI 与启动入口 | 构建、所触及行为的 smoke phase、binary tests |
| Headless 与拟议 eval CLI | headless、CLI 及参数帮助测试，配套离线评估案例 |
| 公共事件或导出接口变动 | api_surface 与文档构建 |
| 内存敏感读取与报告 | 对应内存测试，验证流式读取和有界输出 |

进程恢复与清理在 Linux 和 macOS 分别验证。macOS 通过不能替代 Linux 的
进程组、setsid 和进程探测测试。故障注入测试使用临时工作区与受控子进程，
不连接真实提交、发布或交易服务。测试不得覆盖个人配置、会话或剪贴板。

性能验收使用相同文件系统与 fixture 比较开关前后的持久化耗时、UI 输入延迟、
日志体积和峰值内存。逐项公布原始测量条件；持久化屏障不能被省略来换取好看的延迟。
写入队列和报告读取必须有界，超出容量时施加背压或报告错误，不能无限缓存输出。
