# View 流：长的 inline-view 内容流进 scrollback

## 问题

替换 composer 的那些 inline view 画的是一个**由内容驱动的带框主体**：builder
（`ui::mcp_view_lines`、`ui::hooks_view_lines`、`ui::config_review_lines`、
`ui::background_view_lines`）把整页作为行产出 —— 上边框、标题、内容、提示、
下边框 —— 而高度辅助函数预留 `lines.len()` 行，再夹取到终端
（`ui::layout::view_height`）。绘制曾是一个普通的顶部对齐 `Paragraph`，于是比
终端更高的主体会悄悄**在底部被裁掉**：一个描述很长的 `/mcp` tool 详情页丢掉了
它的参数尾部、它的 `Esc to go back` 提示、以及下边框 —— 框就这么跑出屏幕，没有
任何迹象表明还有下文。

一个 inline 区域没法像全屏 pager 那样在内部滚动 —— 它也不该：这个 TUI 的整个
设计就是让已完成的内容住在**终端真正的 scrollback**里，由终端自己的滚动去读它
（对话就流到那里；权限 prompt 在发问期间把聊天挤到那里，
`docs/state/permissions.md`）。所以修法是把 view 的内容按 TUI 呈现其他一切的方式
呈现出来：作为文本。

## 设计

两条规则，都是 `ui` 里的纯策略，由边界执行：

1. **带框的 view 主体底部对齐。** 当构建出的行数多于区域给它们的行数时，绘制
   显示**最后**那些行 —— `ui::view_body_skip` 决定跳过顶部多少行 —— 于是可交互
   的尾部（操作行、提示、下边框）始终在屏上。隐藏光标的座位
   （`menu_marker_seat`）减去同一个跳过量，于是光标停在上面的那个 `❯` 正是
   真正被画出来的那个。一个没有画出任何 `❯` 的页面 —— 一个详情视图、一个未配置
   的 `/mcp` 列表、一个锚点已滚出视野的高亮 —— 只坐落在它最后一行文本之后，
   即收尾提示处（各 overlay 的 `overlay_cursor_seat` 规则；边框规则属于装饰，
   会被跳过），而只有短到连提示都画不出的区域，才退回远端角。
2. **被跳过的顶部流进真正的 scrollback。** 当页面超出它那条被画的尾部所得到的
   行数 —— 对一个带框视图来说是整个终端（主体被 `view_split` 钉在底部，后者先
   挤压条带），对条带来说是条带自己那一片 —— 那些被隐藏的顶部行**提交到 live
   区域之上**，正是它们视觉上该在的地方：scrollback 以页面顶部结束，屏幕显示
   页面尾部，而终端自己的滚动把整件事当作一件读。`ui::view_flow` 就是那个纯的
   决定 —— 哪些行流、以及一个标识所流状态的**签名**（在本宽度/行数下这些流的行
   的文本，或者 —— 对一个会 tick 的页面 —— 一个给它命名的稳定键；见下）。

签名算什么，是按 view 各自的选择（`ui::view_flow` 的 `FlowSign`）。一个只在
**按键**时变的页面，签的是它的**行** —— 对它们的任何编辑都会重新签，重建就会
重新流新的那些。除了那两个自己会动的页面，其余每个页面都是这样：**流式条带**
（`docs/ui/strip-flow.md`）和 ↓ manager 的**详情**页会活跟一个正在跑的 shell，
于是它的运行时长、它的输出框、它的 `Showing N lines` 说明都在按键之间在动，节奏
是打开的条带一直跑着的 32 ms（`App::wants_animation_frames`）—— 条带以同样的
节奏动，原因也一样。给这样的行签名，会每秒 purge 重建整屏三十次，所以它们各自
签的是**自己是谁的**（`FlowSign::Frozen`）—— 页面所描述的那个 shell、条带所
显示的哪个 call —— 而流出去的顶部**冻结**在它被提交的地方 —— 一次 resize、走回
列表、或换到另一个 shell 仍会让它重新签名，因为两种情形里行数与宽度都被哈希进
去了。冻结的文本正是 scrollback 为屏上其他一切所持有的东西，也正是所报告的那个
bug 要求的：*「如果它不在终端窗口里显示，就冻结它，而不是把细节删掉。」*

流出去的行不是历史，所以它们过期时不许留下任何东西。边界（`tui::view`）记住它
上次流的东西的签名（`Session::flowed_view`），遇到任何不匹配 —— 页面导航了、
搜索收窄了、菜单关了、终端 resize 了 —— 就以标准的 **purge 重建**作答
（`repaint_conversation` / `repaint_agent_view`）：scrollback 由历史重建，把
*当前的*流行追加到尾部；view 关闭时则一行不追加 —— composer 就这么回来，而任何
陈旧的 view 文本不会在任何地方幸存（`/clear` 的那套机制；`term::reflow`）。一次
流进行中时，scrollback 的**提交暂停**（`Session::commits_allowed`，agent 会话
视图那套模式）：在流行与区域之间提交一个单元格，会把带框的内容撕成两半，所以它
在历史里等着，由流退出时的重建重新生成。飞行中的部分回复以它在每次 purge 中都
幸存的那种方式幸存：它住在流式缓冲区里，第一次未流的重建会重新提交它
（`docs/ui/flicker.md`）。

流的尾部贡献像每一笔重建写入一样被夹取（`RESIZE_REFLOW_MAX_ROWS`，保留离区域
最近的那些行），于是一个病态的页面没法把一次导航变成一次无界的写入。

## 边框紧贴内容

每一个带框的 inline view —— 各个 picker、菜单、页面、↓ manager 条带以及两个模态
框 —— 都是一条上边框、它的内容和一条下边框，别无其他：开口边框下面没有空行，
收口边框上面也没有。边框*就是*框的边，所以边框之内的一个填充行说不出任何边框
没说过的话；而在一个与上方对话共享终端的 view 上，那一行是把对话里的一行白白
推进 scrollback —— 每页两行，每一页都如此（所报告的浪费：`/model` picker 在
一个空行上打开，又在另一个空行上收口）。空行仍然分隔页面*内部*的各块 —— 搜索行
与列表之间、列表的计数与它的详情之间、描述与提示之间 —— 因为在那里它们说的是
一件事到哪里结束、下一件从哪里开始。

```
────────────────────────────────────────────
  Select model
  Applies to this session and new ones in this directory
                                             (blocks keep their gaps…)
  ❯ cla

  → anthropic/claude-3-haiku [openrouter]
    claude-opus-4-8-fast [a0_venice] ✓
    (1/12)

    Model Name: Anthropic: Claude 3 Haiku
────────────────────────────────────────────  (…but nothing hugs a rule)
```

光标座位从那条边算起：picker 的 `❯` 搜索行是在构建出的页面里**找到**的
（`view_prompt_row`），而不是钉死的 —— 在有空间容纳它的页面上位于它的横幅之下，
而一旦短终端的一级级阶梯把它舍弃，就直贴在上边框之下（*紧凑页之下*）—— `/login`
某条问题的标题以同样方式找到（`title_row`，页面第一行文本），它的设备码页的座位
是第 1 行（`DEVICE_CURSOR_ROW`），而一个权限 prompt 的选项坐在区域底部之上
`PERMISSION_TAIL_ROWS` 处 —— 空行、提示、边框。`/mcp` 认证页的 `URL >` 字段
是在绘制所构建的那个页面里**找到**的，而不是从底部数出来的，因为它下面的注记会
换行。每个 view 的测试都用一条共享断言（`assert_frame_hugs_content`）
走一遍它的各个状态，所以一个给边框加了填充的页面会挂掉它的测试套件。

## 一个 picker 的页面

搜索行 picker —— `/model`、`/settings`、`/skills`、`/theme`、`/mascot`、
`/spinner` —— 和 `/login` 的各页是同一个形状，于是眼睛在每个上面都在同一个地方
找到同一个东西（`model_view` 的 `picker_header`、`picker_page`、
`marked_row_head`、`list_counter_line`）：

```
────────────────────────────────────────────
  Settings                                   the title, the pages' dress
  Changes take effect at once and persist …  what a choice changes, dim
                                             gap
  ❯                                          the search line
                                             gap
  → Hide thinking        false               the window: `→` under the `❯`
    Verbose output       false
    …                                        (five rows; /model 7, /theme 10)
    (1/20)                                   the counter, under the names
                                             gap
    Hide the model's chain-of-thought …      the highlighted row's detail
                                             gap
  Type to search · Enter/Space to change …   the hint
────────────────────────────────────────────
```

- **每页一个 `❯`，即搜索提示的那个。** 每一行列表都从框的内缩与 `→` 标记
  （`MODEL_MARKER`）开始 —— 或者从那标记宽度的空白开始 —— 于是标记在 `❯` 之下，
  而名字在标记之下对齐。带预览的 picker 过去用第二个 `❯`（`/mcp` 列表的那个）
  标记选中项，读起来像第二个提示；无文本输入的菜单（`/hooks`、`/mcp`、启动审查、
  `/donate`）保留 `❯`，因为它们没有搜索行会让它被混淆。
- **详情挂在名字之下**（`MODEL_DETAIL_INDENT`）：`(n/total)` 计数器、高亮行的
  描述、`/model` 的 `Model Name:` 行，以及它那些失败 provider 的理由。标题、搜索
  行、占据列表位置的占位符、以及提示，都保持框的内缩。
- **一个横幅点名这个页面**：一个标题，用各页标题的装束，压在一行暗色文字之上 ——
  `/skills` 是目录条目数，其他则是选一个会改变什么、以及它保存在哪里
  （`Changes take effect at once and persist across sessions`、
  `The startup banner's art — saved for this directory`）。它换行而不裁切，而
  每个副标题在 60 列的终端上都能占一行放下。
- **窄窗口。** 五行（`SETTINGS_MENU_MAX_ROWS`，`/skills`、`/mascot` 与
  `/spinner` 共用；`/model` 是七行），选中项骑在中间，计数器在它们之下说明它站
  在哪。`/theme` 保留十行（`THEME_MENU_MAX_ROWS`）：它的各行与计数器并不比旁边
  的预览更高，所以几乎整个目录都显示出来，而在高度上不付代价。带预览的 picker
  也数（那里的行数），而它们过去用 `↑ N more above` / `↓ N more below` 行来点名
  窗口藏了什么：在一个窄窗口上，那些会随选中项移动而来去，页面也会跟着跳一行。
- `/login` 的根页用文字提问 —— `Select login method` 压着它那三条进入方式 ——
  因此完全没有搜索行：打字什么也不做，光标在那里隐藏，与登录方式选择页一样，而它
  的阶梯把标题留在搜索行的座位上，隐藏的光标坐在它上面，无论各等级把它留在哪里
  （`docs/providers/copilot.md`）。

## 先丢行、再流的页面：紧凑页

底部对齐把页面的*尾部*留在屏上，对一个选项坐在底部的页面来说这是对的 —— 权限
prompt 的选项、`/mcp` 服务器页的操作。picker 是另一个形状：它的 `❯` 搜索行与
高亮行坐在靠近**顶部**的地方，在页面横幅之下，而它的描述或预览坐在列表下方。
在一个短终端上做底部对齐，这样的页面会留下描述和提示，而把搜索行与列表顶部流进
scrollback —— Enter 将作用的那一行，只有把终端往上滚才够得着。

所以 picker 的 builder 收下它可能得到的行数，并构建**第一个装得下的页面**
（`model_view::first_page_that_fits`），从最完整的试起，而让位的正是选项不需要的
东西，按 codex 的顺序（`selection_picker_layout.rs`：*「可选的空行和预览先让位；
横幅、tab、搜索、至少一条结果保持可见」*）：

1. 一段长描述被裁成一行（`Description::OneRow`），页面有描述时如此 —— 一段会
   换行的描述让页面高度随选中项移动，而一个只按高度做决定的页面，会在 ↑/↓ 越过
   一条长描述时，在完整版与紧凑版之间来回翻；
2. 描述、预览和 `(n/total)` 计数器走开，列表变成两个预留溢出槽之间的一个
   `COMPACT_LIST_ROWS`（3）行窗口（`model_compact_list`），在横幅仍装得下时留在
   横幅之下（`model_view::compact_page_with_header`）：codex 的箭头行，`↑ N more
   above` 紧贴搜索行之下，`↓ N more below` 紧贴提示之上，哪边没藏东西哪边的槽
   就是空的，于是框在每个选中项下都是同一个高度，而一个空槽正是页面本来就想在
   那里要的空行 —— 这也是为什么槽从不贴着边框：一个在上边框与列表之间没有自己
   任何东西的页面（没有横幅的 `/secrets`、`/donate` 那个孤零零的地址）不保留槽，
   因为在那里一个空槽就正好是*边框紧贴内容*所禁止的那个填充行；
3. 横幅最后走：去掉它之后的同一个紧凑页，搜索行直接贴在上边框之下。

高度来自两处：预留高度与流的遍历拿终端的高度，而绘制与光标座位拿已为页面预留的
区域的高度 —— 至少是所选页面的高度，至多是终端的高度 —— 而一个取「第一个装得下
的页面」的 builder，从哪一处都挑到同一个页面。

### 紧凑页之下：搜索行永不消失

一个再没有阶梯可退的页面就底部对齐，而把 picker 的紧凑页底部对齐，对它做的正是
它曾对整页做过的事：在一个只比它短一两行的终端上，搜索行流进了 scrollback ——
而硬件光标无法坐在一个 scrollback 行上，于是被夹到主体顶部某个主题或设置项上
—— 再短两行，高亮行也跟着去了。所以搜索行 picker（`/theme`、`/skills`、
`/settings`、`/mascot`、`/spinner`、`/model` 以及 `/login` 的各列表）不在紧凑页
停下。它是八级阶梯中的第一级（`model_view::compact_page`），每一级比上一级短一
行，但溢出对消失的地方是个例外 —— 那里一次掉两行 —— 而没有搜索行的页面，用它的
标题占住搜索行的座位来共用这套阶梯（`/login` 的根页与它的登录方式选择页、
`/usage`、`/context`）：

| 行数 | 页面保留什么 |
| ---- | ------------------- |
| 9 | 边框、搜索、`↑`、三行、`↓`、提示、边框 —— 紧凑页，与每个页面一样贴着上下两条边框 |
| 7 | `↑`/`↓` 对走开 —— codex 只在三条结果旁边预留它的箭头行 |
| 6 | 上边框走开：这么短的页面填满终端，屏上没有任何东西在它之上需要被区分开，于是搜索行开启屏幕 |
| 5、4 | 列表行走开，三行到两行到一行 —— 即高亮的那一行 |
| 3 | 下边框走开 |
| 2 | 提示走开 |
| 1 | 高亮行走开，只剩搜索行 |

于是在任何至少一行高的终端上，页面都装得下，它没有任何东西要流，而插入符坐在
搜索行上查询之后 —— 在构建出的页面里**找到**（`view_prompt_row`），绝不钉在
第 1 行，因为阶梯会把它往上挪。`/model` 没有提示行，它把 `Model Name:` 行留在
提示的位置上，所以同一套阶梯照用。一个无物可选的页面 —— 搜索什么都不匹配、列表
还在加载、目录为空 —— 把它的占位符放到列表的位置（`placeholder_window`：页面还
保有三行时整块显示，之后显示它的前几行），并以同样的方式丢行，于是打进去的东西
留在占位符上方可见；一个列表下方无物的页面（`/model` 的占位符）在占位符上收口，
省掉那个会贴上它下边框的空 `↓` 槽。

目前的紧凑页：`/theme`（`docs/ui/theme.md`）、
`/skills`（`docs/tools/skills.md`）、
`/settings`（`docs/state/settings.md`）、`/mascot`（`docs/ui/mascot.md`）、
`/spinner`（`docs/ui/spinner.md`）、`/model` 与 `/login` 的各列表
（`docs/providers/llm.md`）、`/secrets` 列表（`docs/state/secrets.md`）；以及
`/donate`，它的列表是框而不是行，所以它在开窗之前先折叠 —— 先是一个手风琴，高亮
不在的那些地址折叠成它们的标签行，而高亮那个保住它的框；然后只剩高亮的地址，它
带编号的标签说明它排第几（`docs/ui/donate.md`）；以及 `/context`，它先丢详情的
尾部、再把它那些用量行一路丢到最后一个请求、然后丢它的条和副标题 —— 标题折成
一行，带上窗口的填充 —— 最后丢图例之前的那行用量，之后图例在紧凑页的阶梯上围绕
高亮开窗，以那行标题为锚（`docs/architecture/context-usage.md`）；以及
`/usage`，
它先丢它的链接，然后把除高亮之外每个订阅都折到它最满的上限 —— `/donate` 的
手风琴 —— 再把标题与副标题折成一行，带上数字有多新，最后落在紧凑页的阶梯上，
每个订阅一行折叠行，在那行标题之下围绕高亮开窗（`docs/providers/usage.md`）。
`AskUserQuestion` 模态框走同一类阶梯（`docs/tools/ask.md`）：它的选项描述先
让位，
然后是它的行围绕选中项开窗，而它那条问题 tab 的 chip 条最后走，即 codex 那套
「tab 留得最久」的顺序。`smoke.sh` Phase 139 在一个 12 行的终端上打开它们，
搜索行 picker 还在 7 行上测过。

## 范围 —— 哪些 view 会流

- **流 + 底部对齐**：每一个由内容驱动的带框 view —— 浏览类菜单（`/mcp`、
  `/hooks`、启动审查、`/donate`、`/export`、`/context`、`/usage`、`/secrets`）
  *以及*带窗口的 picker（`/model`、`/login`、`/settings`、`/skills`），现在全都
  是行 builder（`*_view_lines` / `key_onboarding_lines`，高度即构建出的行数）。
  它们的内容**按状态是静态的**：只在用户按键时变，所以 scrollback 里那些冻结的
  行在两次签名检查之间绝不可能过期。资格判定与 `render_live_with_preview` 的
  优先级一致：一个 view 只在它确实是那一个被绘制出来的东西时才流（一个 ask 或
  权限模态框盖住它下面的一切）。`/context` 是这里唯一一个行也会在按键之间移动的
  页面 —— 它随对话重新计数 —— 但只在事件上，绝不每帧，所以它像其余的一样按自己
  的行签名；它的阶梯落在它那行标题上，所以像搜索行 picker 一样，它从不真正流
  （`docs/architecture/context-usage.md`）。`/usage` 同理：它的行随它的读取和
  倒计时移动，在事件上或一个慢钟帧上，而它的阶梯落在它那行标题上
  （`docs/providers/usage.md`）。

  搜索行 picker 保持有资格，却从不真正流：它们的 `❯` 搜索行坐在页面**顶部**，
  一次流会把它带进 scrollback，所以它们的 builder 改为一路丢行丢到搜索行（上面
  的*紧凑页之下*），于是每个页面都装得下终端。它们保持有资格，是为了万一哪个
  builder 冲出了头，也仍然是把它的顶部流出去、而不是丢进一个不存在的缓冲区；
  那时硬件光标会夹在主体顶部（`anchored_view_row`，即座位那套跳过减法），它对
  `/login` 的 key 步骤仍是这样，后者的字段坐在它页面的脚部，锚点把它留在那里。
- **流 + 底部对齐，带一条 context 规则**：tool 权限 prompt
  （`docs/state/permissions.md`）。它的主体 —— 带编号的写/diff、命令 —— 现在
  **完整**显示（退役的上限把中间藏在一个 `… +N lines` 尾部后面；那个尾部只在
  越过 `PERMISSION_BODY_MAX_ROWS` 安全上限之后才保留，因为页面每个绘制 tick 都
  被重建并高亮）。尾部那一块 —— 问题、选项、提示 —— 收口页面，所以锚点把它留在
  屏上；↑/↓ 重新给被画尾部之内的行上色，所以流出去的顶部保持它的签名。框之上的
  **context 单元格**像其他一切一样搭乘这次流，但有一个条件 —— 它们必须是*静态的*
  （`context_is_stable`）：一个排队的 `⎿ Waiting…` 单元格是，因为 approve 接缝
  在它的 `ToolStart` 之前运行，而答案待定期间没有什么能改变，所以它整块、不折叠
  地流进 scrollback（已经没有满屏的东西要争，所以一个 `… +N more waiting` 摘要
  会白白藏起兄弟）。一个**活的 agent 组**或**正在运行的 call** 则不是 —— 树的
  圆点随框的脉冲闪烁，它的计数器在推进，一个运行中 call 的流式输出会让它的窥视
  增长 —— 而一行流出去就冻结在 scrollback 里，所以会 tick 的内容要么在那里过期，
  要么每个 tick 都把这次流重新签成一次 purge 重建；那份 context 让位，只有静态的
  框会流。把静态单元格丢掉才是所报告的回归：它让 prompt 变成一个无来由的框，而
  那个单元格不在任何缓冲区里。builder 在区域真正得到的那个高度上仍是同一个不动点
  —— 不带预算地构建流出去的 context，正是让页面在那里与 `term_height` 无关的
  原因 —— 所以 `permission_height` 与 `render_permission` 绝不可能意见不一。
- **流（冻结）+ 底部对齐**：↓ 后台 manager（`docs/tools/background.md`）。只做
  锚定就是所报告的 bug：在一个只比详情页短几行的终端上，上边框、`Shell details`
  标题以及状态/运行时长字段被跳进**完全无缓冲区**的地方，于是把终端往上滚，对话
  会直接撞上一个无头的框。它们现在像其他每一页一样流 —— 区别只在流签在什么上。
  它的**列表**页在按键时变，所以像菜单一样按行签名。它的**详情**页会 tick，所以
  它签 shell 的 id，流出去的行被冻结（见上）。一个流了出去的运行时长读的是页面
  被提交时它有的那个值，直到有什么让流重新签名 —— 陈旧，而在那之前它是*芳踪全
  无* —— 而屏上那个页面仍旧跟活、不变，一如从前。哪些行流，取决于终端多短：页面
  是 24 行，所以 23 行时只流上边框，18 行时流整个字段块；输出框要到 15 行才开始
  流。一个 shell 已消失的详情视图渲染的是*列表*（`background_view_lines` 的防御
  性回退），所以它按列表的方式签名。
- **流（冻结）+ 底部对齐**：**流式条带**本身（`docs/ui/strip-flow.md`）—— 运行中
  的 tool 单元格、`● Thinking…` 块、活的 agent 树、spinner 状态行、排队的消息、
  toast。它是区域里唯一的弹性内容，所以 `preview_budget` 过去会*扔掉*它负担不起
  的那些行：在一个 13 行的终端上，一个运行中的 `bash` call 丢掉它的 `+N lines`
  页脚和它的 ctrl+b 提示；在 9 行上丢掉它整个输出块；在 4 行上丢掉状态行。
  `ui::live::strip_lines` 现在把它当作一页来构建，`render_strip` 经
  `render_framed_tail` 绘制它，于是条带保住它最新的行，而它的头部流出去。冻结，
  理由与条带详情页相同：条带以回合自己的 32 ms 节奏移动，所以它签的是
  `ui::live::strip_flow_key` —— 条带是*谁的* —— 而不是它的行。流式回复的**前沿**
被排除在外：`StreamRender` 已经提交了它完成的行，所以它丢掉的没有任何东西丢失，
而流它会导致每个 chunk 都重新签名。只在 composer 在屏上时如此 —— 一个替换
composer 的 view 用 `view_split` 分割区域，那里流的是那个 view 的页面。
- **流 + 底部对齐，逐页**：`AskUserQuestion` 模态框（`docs/tools/ask.md`）。它的
  builder 和其他一样是行 builder —— 每个*页*一个扁平行列表（一个问题 tab、
  Submit 复核页），并排的预览面板只在这些行之内横跨 —— 里面没有任何东西会 tick：
  chip、选项与输入字段只在按键时变。所以每一页都像 picker 一样流：尾部那一块
  （选项、提示、收口边框）收口页面并留在画面上，被跳过的顶部（chip 条、问题、
  头几个选项）流出去，一次 tab 切换或一次作答把流重新签成 purge 重建（搜索行
  规则），而只动尾部的 ↑/↓ 保住它。退役的「丢顶部」夹取反而把那些顶部行裁进
  *不存在*的缓冲区 —— 在小终端上，模态框打开在选项中段，而它的问题够不着，就是
  所报告的「它把文字藏起来了」。

## 为什么不……

- **……做个内部滚动（框里的 pager）？** 它会把内容困在一套新的按键语法之后
  （↑/↓ 在这些菜单里已经用来移动选中项），并困在一个终端自己的滚动够不着的窗口
  之后。本代码库的先例正相反：权限 prompt 故意把被挤开的聊天滚进*真正的*
  scrollback，好让用户「能在它发问期间把终端往上滚、重读任何东西」。
- **……把区域本身做得比屏幕还高？** `term::InlineViewport` 把区域当作一个屏幕矩形
  来绘制；屏幕顶部之上的行按定义就是 scrollback，而那正是流所提交的东西。重用
  重建路径意味着没有新的 viewport 机制 —— `write_above` 早就能把区域安置在一个
  任意长的尾部之下。
- **……让 ↓ manager 的详情页像其余的一样按行签名？** 它 31 fps 地 tick，于是每帧
  都会重新签名并换来一次 purge 重建 —— 整屏每秒被擦掉重写三十次，既丢掉用户的
  滚动位置又闪。冻结流出去的顶部是这个取舍：那些行变得陈旧，而不是缺失。
- **……把页面缩小（更少的 `BG_OUTPUT_ROWS`）好让它永远装得下？** 那会在正需要其
  输出框的终端上改动详情视图本身，去解决一个流已经解决了的问题。条带自己的 TUI
  不受这个修法影响。
- **……权限 prompt 那套截断加补行（`… +N lines`）？** 它把选项留在屏上，却藏起
  内容的中间 —— 正是这里的抱怨。它对*prompt* 仍然合适，因为它的 context 行会
  tick（一棵活的 agent 树），而它的答案不该等一次滚动；一个浏览页的内容才是那页
  的意义。

## 它倚靠的不变量

- 不变量 3（内容锚定的 viewport，经 `term::reflow` 重建）：流搭的是每次 resize
  和历史倒回都在用的同一次 purge 重建；`write_above` 把一个长尾部滚进空
  scrollback，正是流所需要的座位。
- 不变量 4（`commits_allowed` 把关）：在一个流着的 view 之下暂停提交，是
  agent 会话视图那条规则应用到第二个盖屏 view 上。
- 签名检查在绘制之前的 draw tick 里跑，于是一次流与显示它的那一帧原子地建立/
  刷新/清除。
