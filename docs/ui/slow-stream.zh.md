# 慢速流 —— 每秒几个 token 穿过内联管线

日期：2026-09-20

## 问题

dummy 后端以**每 45 毫秒一个词**的速度流式输出它的罐头回复，smoke 套件就以这个节
奏驱动每一条内联渲染的保证。而一台吃力机器上的真实模型 —— 笔记本 CPU 上的 7B 模
型、一个饱和的 API —— 流式输出的是 **token** 而不是词，速度是每秒两到七个。在那
个速度上有两件事变了，而且都不是程度问题：

- **每个中间状态都在屏幕上停留得够久，久到能读。** 45 毫秒时，一个半开的 `**`、
  一个围栏的第一个反引号、一个还没有标题文字的 `##`、一个分隔行还没到的表头，全
  都在一帧动画之内掠过。300 毫秒一个 token 时，其中每一个都是*用户会盯着看的一
  帧*，而一条已经提交进 scrollback 的行有三份之一秒的时间，让框上方那条条带与它
  矛盾 —— 把它显示第二遍，或者换个样子显示。
- **chunk 的边界落在按词切分永远不会落到的地方。** 真实 tokenizer 的片段会把
  `**bold` 切成 `*`、`*bo`；把一个围栏的开头切成一个反引号一个；把一次段落分隔连
  同下一行的头几个字一起放进一个片段。`stream::chunks` —— 每个脚本化 demo 都按其
  流式输出的那个按词切分 —— 一个都产生不出来，所以从来没有任何东西真的把边界从它
  们身上驱动过。

所以问题不是「渲染器在每一个前缀上都成立吗」（它成立 ——
`stream_render_is_prefix_stable_over_every_prefix` 与那锅敌意浓汤的 fuzz 早就把
语料的每一个*字符*前缀都驱动过了），而是「当那些状态持续存在时，**终端**成立
吗」：循环发射的帧、它清空的行，以及一个不认同步更新的终端会呈现成什么样。

## 架子

三样东西，都可复用，好让答案一直可查：

- **`ZEROTH_CHUNK_DELAY_MS`** —— dummy 在每一段流式输出的回复文字（以及每一行实
  时的 tool 输出）之后停顿多久：除非设置，否则是 `stream::CHUNK_DELAY` 的 45 毫
  秒。`ZEROTH_STARTUP_DELAY_MS` 的孪生兄弟，以同样的方式穿线
  （`DummyAi::with_chunk_delay`、`tui::config::chunk_delay`，`stream::dummy` 里
  那唯一一对 `replay`/`pace`）。`ZEROTH_CHUNK_DELAY_MS=400 zeroth` 然后 `stream
  some markdown`，就是这份文档的交互形式。
- **`stream::tokens`** —— `chunks` 的压力孪生：token 大小的片段，走一个平均三个
  字符的长度循环（`TOKEN_LENGTHS`，一字符与两字符的片段也在内），凡是一串标记字
  符（`*_~` `` ` `` `#-|=>:` 与数字）本来会整段骑在一个片段里的地方就切开，于是
  渲染器据以给一行分类的每一串，都是**一个字符一个字符**地流过去的：`**` 是 `*`
  + `*`，一个围栏是三个片段，`|---|` 是五个片段，`10.` 是 `1` + `0` + `.`。提交
  器携带的每一个部分标记谓词 —— `has_unsettled_block_prefix`（部分围栏、标题、分
  隔线与列表标记的检查，在每个容器层级上）、`has_open_inline`、`has_forming_url`
  —— 在每一次出现上都被演练到。确定性的（smoke phase 按片段数给一个回合计时）、
  忠实的（片段拼接回输入）、绝不长于 `TOKEN_MAX_CHARS`、绝不把一个字符切成两半。
- **`markdown` 场景** —— 一个提到 "markdown" 的 prompt 会播放
  `stream::MARKDOWN_TOUR`，一份带着渲染器所知道的每一种块类型的文档：一个 `#` 标
  题压在一段换行的段落上、`**bold**`、`*italic*`、`~~strike~~`、`` `code` ``、一
  个 `[link](…)` 与一个裸 URL、一个会换行并嵌套到三层的项目符号列表、一个带两位
  序号的有序列表、任务条目、两行的引用块、一个 Python 围栏，**里面有一行空
  行**（是内容，绝不是段落分隔）、一个 Rust 围栏，其签名**超过八十列**（一行被暂
  扣的多行）、一个三列且含两列 emoji 的表格、一条 `---` 分隔线、一个 `###` 标
  题，以及交还。它是**一条纯文本消息** —— 没有思考阶段、没有 tool call，没有任何
  东西来切分这条回复 —— 所以增量渲染器从它的第一个字符一直携带到最后一个，而且它
  是**按任意两行内容的渲染结果都不相同** 写的，正是这一点让 smoke phase 能把每一
  行精确地数一次。它在注册表里排在 `table` demo 之下（「markdown table」的
  prompt 指的是那一个），并带着文件与 agent demo 都带的那个 `/init` 守卫，因为
  `/init` 的罐头 prompt 要的是 Markdown 标题。

`scripts/smoke.sh` **Phase 121** 在一个 80×24 的终端上以每片段 90 毫秒流式输出这
次巡游（约 65 秒，约 720 个片段），同时在旁边一个 40×12 的终端上以 45 毫秒再跑一
遍，那里签名折成三行、表格回退成键/值记录、预览位只有几行。它从三个方面盯着这一
回合，每秒大约十几次（整个回合 800 来个样本）：

1. **Scrollback 只追加。** 终端历史的每个样本（一次 `capture-pane -S -`，在屏幕
   高度处切开 —— 也就是已经滚出可见屏幕的每一行）都必须是下一个的前缀。一条变
   了、挪了或被写了两遍的已提交行，会在这里现形。而且**框绝不往上跳**：这个区域
   是内容锚定的，所以一次提交把页脚往下推，直到它到底为止，也没有东西把它拉回来
   —— 一个页脚行比上一个样本更靠上的样本，就是一次弹跳。
2. **没有内容行在屏幕上出现两次。** 三十三个短语，巡游里每行一个，在历史加可见屏
   幕里被数一遍；任何大于一的计数都是重复。`committed ++ preview` 在每一瞬都是那
   条回复（一个前沿的约定，`docs/ui/markdown.md`），所以一行已经提交、而条带还在
   预览它 —— 就是慢速流的重复行形状，在这个节奏下会在屏幕上待三份之一秒 —— 会以
   计数二的形式现形。一个重复必须存活**两个连续样本**才算：`tmux capture-pane`
   是按字节解析读网格的，所以单个样本可能抓到一次同步更新做到一半，而那正是 mode
   2026 存在的意义所要藏起来的瞬态。
3. **字节流**，用 `tmux pipe-pane` 录下来：同步更新内部的每一次 live 区域清除
   （Phase 15 的规则，作用在一个长上百倍的回合上）—— 以及在下面那处改动之
   后，**根本没有 live 区域清除**。

然后是沉降后的 transcript：三十三个短语必须各出现恰好一次，按文档顺序，页脚在最
后一行，屏幕上只有一个 composer，而且网格的每一行宽度相同。

## 这次跑出来什么

**纯**的那一层本来就是对的，在新的切分下也仍然
对：`the_markdown_tour_streams_prefix_stable_at_every_width` 在宽度 20、40、80
上把巡游的每一个字符前缀送进那条差分不变量，而
`the_markdown_tour_never_previews_a_committed_row_token_by_token` 驱动 dummy 实
际流式输出的那些 token 片段，把条带限制在 80×24 区域所能预留的量内，断言没有任何
非空的预览行已经躺在 scrollback 里，并且被限制过的预览总是尾随。

**边界**把两个 session 都渲染对了：每个短语一次，按顺序，框贴着底部，网格对齐，
同步帧之外的清除是 0 次。而录音还说了些别的，来自一个 65 秒的回合：

| 帧数 | 字节 | 形状 |
| --- | --- | --- |
| 2 184 | 361 KB | 整个回合，约 33 fps（状态链的 32 毫秒） |
| 2 065 | — | 300 字节以下：spinner 与计时器，各一次 diff |
| 49 | 107 KB | 一次提交：`ESC[J` 清空 live 区域，然后一次完整重绘 |

最后那一行就是这次的发现。`write_above` —— ratatui 可移植的 `insert_before` 的移
植 —— 滚动、写入那些已提交的行，然后从区域的新顶端清到屏幕末尾，而 `paint_frame`
把区域重绘进那片空白。在一次同步更新之内，那片空白从未被呈现，这是 Phase 15 所证
明、而 `docs/ui/flicker.md` 所解释的。但一个不认 mode 2026 的终端 ——
Terminal.app、xterm、较老的 VTE —— 在它自己的刷新到期时，会把已经解析到的任何东
西渲染出来，而一帧提交平均 1.6 KB、最宽时 3.9 KB，对比一次 4 KB 的 pty 读。一帧
被切成两次读、而 `ESC[J` 在第一次里，就是一帧被呈现出来而**没有框** —— 那个
flicker 修复在同步更新抵达的每一处都消掉了的流式闪烁，在它抵达不到的每一处仍然活
着。45 毫秒一个词时，提交每两秒左右落一次；在慢模型的节奏下，每完成一行就落一
次，于是框会在整条回复的长度里大约每秒闪一下。

采样还发现了第二件事，而它一开始被读成了 scrollback 在变：一次运行里有两回，历史
的 *长度*掉了两行，而那些样本的帧显示框坐在屏幕底部上方两行、下面全是空行 —— 就
在 Python 围栏关闭之后，以及又在 Rust 围栏之后。那是条带。一个关闭的 ``` 不留下
任何未提交的东西（每一行代码都在 scrollback 里，围栏本身不渲染任何行），于是
`StreamRender::preview` 回答的是**没有行**，`preview_rows` 一并不预留，条带就丢
掉了它的预览位*以及它的间隙*：区域原地缩了两行，框跟着缩。下一行的第一个字符把位
子带回来，框又往下掉两行。45 毫秒一个词时整个往返只有一帧；在慢模型的节奏下 ——
巡游一个反引号一个反引号地流过围栏，然后一个换行，然后是下一个开头 —— 每遇到一个
代码块，框就在上面待半秒。

正是为此的一个看守 —— 页脚所在的行绝不能在两个样本之间*上移* —— 在第一件修好之后
抓到了它的小兄弟：每个围栏**开头**处一跳一行。段落分隔之后，条带持有分隔的那个空
行加上尾随那一行；一个反引号一个反引号地流过去时，那一行先是 `` ` ``、再是 `` ``
`` —— 散文，一行 —— 到第三个反引号时是围栏标记，它渲染**不**出任何行。预览从一个
两行变成一行，持续一个 token 之久，然后在开头的换行把一行空代码行放到它下面时又
回到两行。而写进纯差分 harness 的同一不变量，还找到了第三种终端跑从未抵达的形
状：在窄宽度下，一个表头在它的分隔行流式到达时以散文呈现，而在分隔行确认的那一刻
塌进一个更短的网格，又在第一行数据到来时塌成键/值记录 —— 同一批行的一次重排，恰
好更短。

## 改动：原地重绘

那次清除从来就不是承重的。`paint_frame` 的 blit 写入区域里的**每一个单元格**
（`visible_cells` 连空白也发；只有宽字形的影子被跳过，而字形把影子盖住了），所以
提交之后区域所占的那些行，无论原来装着什么都被覆写 —— 上一区域的下半部分，随着滚
动往上挪了。那次清除还盖住的是新区域*下方*、上一块更高的区域所占的那条行带：在一
帧里，一个正在成形的表格整块提交，而条带从它的多行预览塌成一行，区域被往下推的行
数少于它缩掉的行数，旧区域的尾部就留在它下面。

所以 `write_above` 不再清除，而 `paint_frame` 先画、然后只把这些行清空：从新区域
的底部到 `repin.clear_below` 腾出的行数（一次普通的缩小）与 `painted_bottom`（区
域上一次被画时的底部，`scroll_up` 现在把它带过每一次滚动，因为被画过的一行就是屏
幕上的一行）两者中的较大者。区域之下永远是空的 —— 框是最底下的内容 —— 所以多清一
点最多花一行空白，而且那里逐行的 `ESC[2K` 绝不可能闪出任何东西。一个把半解析的提
交帧呈现出来的终端，现在最坏也只是显示一个下半部分比上半部分慢一帧的框。

有两条路径需要一个说法。`clear_scrollback_and_screen`（每一次 purge 重建）把
`painted_bottom` 重置为零，因为一个空屏幕下面没有区域可清；而 `restore`，那唯一
一趟没有后续绘制的冲刷，在退出时的待处理冲刷之后自己清空区域 —— 也就是
`write_above` 的清除在这条路径上一直做的事 —— 于是退出绝不会留下一个撕裂的框。旧
清除所绕开的那个 tmux 顺序问题（「一次完整清除之后紧接一次滚动会把垃圾溢进
scrollback」）在完全没有完整清除之后就不成问题了。

Phase 15 的活性自检也跟着搬了：它过去会在没有清除的录音上失败，作为计量表见过提
交路径的证据；现在它会在没有同步帧的录音上失败，而 Phase 121 把 `clears=0` 钉成
了设计。

## 改动：预览在两次提交之间绝不缩

条带是区域里唯一有弹性的内容，而两个 token 之间，一条还在流式输出的回复除了前沿
之外什么都没变 —— 所以它预留的行绝不能*缩*，除非有行搬去了 scrollback。写成一条
不变量：**预览丢掉的行绝不多于这一步所提交的。** 三种形状都破坏它，而没有哪条逐
形状的规则能覆盖第三种（一次表格重排是更短还是更高，只有布局知道那个量），所以
`StreamRender` 保留一个**地板**：上一次预览的高度，被 `commit` 每次搬去
scrollback 的行所降低，而 `preview` 用空行把它自己的行补到那个高度 —— 也就是下一
段内容将要落上去的那些行。关闭者那种情况保住位子与间隙；开头者那种情况保住一个
token 之前 `` `` `` 散文所占的那一行；表格那种情况保住被换行的表头的行，直到它的
数据行把那些行填满。补的是几何，不是内容：下一段内容占用那些行而不是叠在它们下
面，尾随上限先消耗内容再消耗空行，bullet-home 那种情况不受影响（一条还没提交任何
东西的回复仍然预览它的项目符号），而 `finish` 从不查询预览，所以沉降的回复逐字节
相同。

这条规则住在渲染器而不是条带里，因为只有渲染器知道它一个 token 之前回答了什么、
以及自那之后提交了什么：从一个裸的 `Vec<Line>` 里，条带分不出「一行被暂扣加一个
待处理的围栏」与「一行被暂扣」。一个前沿的约定（`committed ++ preview ==
assistant_lines(prefix)`）为它获得了它唯一的宽容：批量渲染会修剪回复尾部的空行，
所以屏幕上可能持有批量渲染所没有的**尾部空行** （`matches_up_to_padding`）—— 只
有那个形状，别的都不行；每一行内容仍然必须匹配，而一个打开的围栏内部的尾部空行在
两边都是内容。而差分 harness 现在自己就携带这条不变量：在每一个宽度上、对整个敌
意浓汤 fuzz 语料，`assert_stream_matches_batch` 会让任何预览缩掉的行多于该步所提
交的步骤失败 —— 这也正是表格那个形状究竟是怎么被找到的。

smoke phase 自己的跳变看守会用一拍之后的第二次捕获来确认一个更低的页脚，因为
`tmux capture-pane` 可能读到一个半解析的帧 —— 屏幕滚了，区域还没重绘，旧的页脚在
其上一行 —— 而真正的跳变持续一个 token，撕裂的帧只持续微秒。

## 什么保持原样，为什么

- **每一帧都隐藏再显示光标。** 这次运行里有 2 184 次隐藏。Hide 是让一个会拖光标
  痕迹的终端（kitty）在一次滚动上不拖出条纹的东西（`docs/ui/flicker.md`）；它括
  起来的帧都很小（300 字节以下，绝不跨一次 pty 读被切开），所以一个没有同步输出
  的终端实际上呈现不出被隐藏的那个状态。
- **一次提交完整重绘区域**（`prev` 被丢掉，因为行挪了）。区域在新位置上的行绝不
  会与它旧位置的行重叠，所以没有 diff 可算；每行提交 1.6 KB 就是代价。
- **那些部分状态本身** —— 一个直到闭合才被当成字面量的 `**`、一个随层级确定而套
  上样式的 `##`、一行在分隔行确认之前以散文呈现的表头 —— 是条带的，永远不是
  scrollback 的，而在慢节奏下任何流式渲染器显示的也就是这些。把它们藏起来，就意
  味着这一行什么都不显示，那更糟。
