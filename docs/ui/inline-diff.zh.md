# `edit`/`write` 单元格里的字符级 diff 标记

## 问题

一个带编号的 `edit` 单元格把整行 `-` 画在暗红底上、整行 `+` 画在暗绿底上
（`docs/tools/tools.md` → *Rendering*）。那只告诉你某一行变了，不告诉你变的是
**什么**：

```
● Edit(/home/linuztx/hello.txt)
  ⎿  Updated hello.txt (+1 -1)
      1 -Bruce Rivera
      1 +Bruce Rivero
```

两行都是一整块平涂的颜色，所以要找到那处编辑，就得逐字符读这两行、发现 `Rivero`
变成了 `Rivera`。在一行长行上——一个 120 列的函数签名，其中一个参数动了——那是
真的难，而那恰恰是 `edit` 产出的最常见形状：一行的*修改*，不是整行替换。

## 它现在做什么

上面那一对现在渲染成：真正不同的字符被提到一个**更亮**的底色上并加粗，而编辑没
碰过的一切保持那行柔和的底色：

```
      1 -Bruce River█            ← the `a` on the bright red, bold, undimmed
      1 +Bruce River█            ← the `o` on the bright green, bold
```

于是行底色仍然一眼回答「这一行变了吗？」，而标记不必读就回答「变在哪？」。

粒度是刻意的，而它就是整个设计约束：**只有变了的东西被上色。** 两边的
`Bruce River` 完全相同，所以标记它——像词级的一趟那样，把整个 `Rivera`/`Rivero`
都涂上——会在只有最后一个字母变了时说姓氏变了。下面的每一条规则都从这一条落出来：
不跨越未变文本合并、不标记一个只是*靠近*编辑的字符，而对一行被替换而非被编辑的
行，完全不标记。

## 它住在哪里

纯粹表现层，完全在 `src/ui/` 里面：

- **`src/ui/inline_diff.rs`** —— 纯核心。分词、token 级 LCS、相似度守卫，以及
  `-`/`+` 游程的配对。没有终端、没有样式、没有 `ToolCall`：它把 `(sign, text)`
  行映射成变动的**字节范围**。
- **`src/ui/file_cell.rs`** —— 把那些范围套成样式（`row_segments`），这是唯一碰
  主题的地方。

**面向模型的**输出一概不变：`llm::tools` 的 `render_numbered_diff` 仍发出同样的
`{n:>W} {sign}{text}` body，所以 wire 格式、`ToolCall::context_output`、rollout
和推导出的上下文全都没被动过。这层细化是从*解析出的 body 行*推导来的，这也是它在
**旧 rollout** 上也能亮起的原因——一个在这次改动之前 `/resume` 的 session 用新的
高亮渲染，因为没有新字段曾被记录过。

## 配对（哪两行被比较）

`refine_rows` 扫过解析出的 body，找一段极大的连续 `-` 行紧接着一段连续的 `+` 行，
并按位置配对：`removed[i]` 对 `added[i]`，至多 `min(n, m)` 对。一个 `⋮` 的 hunk
间隔、一条 `…` 注记、一行上下文，或一行解析不了的东西，都结束这段游程
（`RefineRow::Break`）。

git 的 `diff-highlight` 在两个游程长度不同时拒绝整块。我们改为配它的重叠部分，并让
下面的**相似度守卫**逐对裁决，因为一次 `-1 +2` 的改动通常仍是第一行的修改加一次
插入，拒绝它就丢掉了用户真正想要的那一处高亮。配错也无害：不相似的行过不了守卫，
退回普通的行底色——正是它们以前渲染成的样子。

## 一对的细化

`refine_pair(old, new)`：

1. **切分**两行为字形簇（`tokens`）——一个簇一个单位，于是组合标记或一个
   emoji-ZWJ 序列保持完整，而每个范围都落在一个渲染器能切开的边界上。
2. **裁掉**共同的前缀和后缀 token。这正是让代价在实践中保持线性的东西——一次典型
   编辑所变的中间部分只有一两个 token，无论这一行多长——也对应
   `llm::tools::diff_lines` 自己的裁剪。
3. **先定界，再对变动中间做 LCS。** 在填任何表之前，守卫那便宜的一半先跑：LCS 只
   能匹配两边都有的 token，所以较小那一边中间的墨迹，是它还能贡献多少的上界，而一对
   即使*在那个上界处*也过不了阈值的，被直接拒绝。它不拒绝任何下面守卫不会拒绝的
   东西，而正是它挡住了一个对满是长而大改行的文件的 `edit` 每行都付一张二次表。
   活下来的做 LCS，由 `INLINE_DIFF_MAX_CELLS` 定界；过了那个界（一行压缩过的 bundle
   行），整个中间在两边都标为变动，而不是跳过——前缀和后缀仍是真实的共同上下文，
   所以那个答案诚实且不花额外代价。
4. **守卫。** 只在两行确实相关时细化：
   - 至少一个共同的**非空白**显示列，并且
   - `common_nonspace * 100 >= longest_nonspace * INLINE_DIFF_MIN_COMMON_PCT`。

   计数排除空白，好让两行共享一个缩进的不相关行不被读作相似，而标点按它值多少算
   ——`alpha()` 和 `zulu_bravo(charlie)` 共享的 `(` 和 `)` 是十九列里的两列，所以
   那一对保持平涂。没有守卫的话，一行被替换的行会回来时布满两段文本碰巧共有的那几个
   字母，那指向不了任何东西。

   因为是*比例*，守卫判的是占比而不是绝对大小：`old = 1` → `new = 2` 只共享它的
   `=`，这一行有五分之四变了，所以它也保持平涂——「整行都变了」是行底色已经说过的
   事，标上除一个字符之外的一切什么也没加。代价是阈值附近的裁决随标识符长度移动；而
   那个带上平涂和细化恰好等值，所以它被留成一个可调的数值，而不是第二个启发式。

   在阈值之下 `refine_pair` 返回 `None`，该行保留平涂底色——一行被*替换*而非被
   *编辑*的行，没有「变的是什么」可指，而把它整个高亮严格地说比一点都不高亮更吵。
5. **合并相邻**的变动单位成游程，于是一个变动的 `z(1)` 画成一块，而不是四粒颜色。

   只合并相邻的。两处变动之间的一段未变文本永不被搭桥，无论多短：`8080` → `9090`
   里的那些 `0` 保持平涂，一行两端各改了一个值之间那段 `and beta = ` 也一样。
   搭桥会给编辑没碰过的字符上色——而那正是这个标记存在所不为的一件事。

## 渲染

`row_segments` 走过这一行的语法高亮片段，在变动范围的边界处切开，并给每一片它最终的
样式：

| | 背景 | 文字 |
|---|---|---|
| `+` 行，未动 | `tool_diff_add_bg()` | 语法颜色 |
| `+` 行，**新增的字符** | `tool_diff_add_mark_bg()` | 语法颜色，在它读不出来时提亮（见下）+ **粗体** |
| `-` 行，未动 | `tool_diff_del_bg()` | 语法颜色，压暗 |
| `-` 行，**删掉的字符** | `tool_diff_del_mark_bg()` | 语法颜色，在它读不出来时提亮 + **粗体**，*不*压暗 |

被删那一行的变动文本刻意逃出这一行其余部分所带的 `DIM`：把视线本该找到的那唯一一段
压暗，恰好击败标记它的目的。

### 变动的文本必须在自己的底色上读得出来

一块底色必须亮到一眼就能找到，所以它落在一个中等亮度上。一个主题里较暗的语法颜色
也坐在那个亮度上，因为它们是为在*编辑器*的暗底上退后而设计的。注释的灰是撞得最狠的
那一个。两者一旦相同，变动的文本就消失进它自己的高亮里：屏幕上评论者本该读的那唯一
一段，正是他们读不了的那一段。被报上来的例子是 Dracula 下一段改过措辞的 `///` 文档
注释，它的注释灰 `#6272A4` 压在它新增文本的底色 `#398153` 上，对比度 **1.0:1**。
整个目录里，注释压在新增文本底色上，在 One Dark 和 Dracula 下读作 1.0:1，在 Nord 和
Monokai 下 1.05:1，在三种暗色 Catppuccin 风味下低于 2:1。没有哪个主题的注释在任一种
底色上达到 3:1。

所以一段变动文本的墨色被扣在 `INLINE_DIFF_MARK_MIN_CONTRAST` 上，即对其底色 **3:1**
的 WCAG 对比度（`wrap::legible_on`，在 `row_segments` 里应用）：

- 一个在那里已经读得出来的语法颜色保留它的颜色。Dracula 的字符串黄在新增文本底色上
  读作 4.2:1，所以一个变动的字符串保持黄色。
- 读不出来的被朝主题自己的文字色提亮（`tool_diff_mark_ink()`），并停在第一个读得出
  来的档位上，于是它保留了底色所允许的尽可能多的色相。Dracula 的注释灰出来是一个浅
  蓝灰，仍是注释的颜色。
- 连主题自己的文字在它自己的底色上都不够的地方（Solarized 的文字在它新增文本底色上
  读作 2.6:1），提亮越过它朝白色走，或者在一个亮主题如 Latte 上朝黑色走——它的墨是
  暗的。
- 一个终端调色板颜色（ANSI 主题）没有值可测，就留成终端所画的样子。
- 只有被标记的游程移动。这一行未变的文本恰好保持高亮器给它的颜色，而一对没被细化的
  行，渲染成它一直以来的样子。

为什么是 **3:1** 而不是 WCAG 对正文要求的 4.5:1：一块中等亮度的底色，限死了任何墨色
在它上面能达到多少。Dracula 自己的文字在它新增文本底色上只读作 4.4:1，它的字符串黄
4.2:1，所以 4.5 的下限会把几乎每一段变动文本变成白色，而不是救回那些消失的。3:1 是
这些主题本就当作可读的对比度：Dracula 和 Monokai 就是把自己的注释放在编辑器背景上
（3.0:1），而 One Dark（2.3:1）、Nord（2.4:1）和 Solarized（2.8:1）把自己的放得更低。
被标记的游程在这一切之上还加粗。

为什么不改为把底色压暗：没有一块比它那一行更亮的底色能承载注释的灰。要让 Dracula 的
注释达到 3:1，底色就得比它所坐的行底色更暗，而到那时它已经不再标记任何东西了。墨色
两边都得动，所以动的是墨色。底色保留它们的颜色。

因为样式在 `code_content_rows` *之前*就被烤进片段，标记能熬过换行——一段跨两显示行的
变动游程在两边都保住它的底色——而这一行结尾的填充保持普通的行底色，于是亮块在变动
文本结束的地方结束，而不是渗到终端的边缘。

## 它在哪里出现

凡是有编号 body 渲染的地方，因为两个构造器共用这一趟：

- 折叠的内联单元格（`file_cell_lines`，被窥视的），
- Ctrl+O 的 transcript 展开（同一个构造器，不设上限），
- tool 权限 prompt 的预览（`numbered_body_lines`），于是你能*在批准之前*看到一次
  `edit` 即将改什么——而那正是「到底变了什么？」这个问题吃重的地方。

一个 `write` 的 body（全新内容，没有符号列）没有对，不受影响，一个 `read` 也是。

## 代价

这一趟是 O(行数)，加上每对的 O(字符数) 做裁剪、O(中间²) 做 LCS——那里的中间对未变的
尾部是空的，对一次典型编辑是一两个字符。字符粒度让中间比词级的长，而这恰恰是前缀/
后缀裁剪和 LCS 之前的定界承担重量的原因。`INLINE_DIFF_MAX_CELLS` 封住最坏情形。live
单元格每动画帧都重渲染，所以裁剪不是一项优化，而是让这个特性在 32 ms 里负担得起的
那件事。

## 调参

全在 `ui/theme.rs` 里：`tool_diff_add_mark_bg()`、`tool_diff_del_mark_bg()`、
`tool_diff_mark_ink()`、`INLINE_DIFF_MARK_MIN_CONTRAST`、
`INLINE_DIFF_MIN_COMMON_PCT`、`INLINE_DIFF_MAX_CELLS`。对比度的算术是
`ui/wrap.rs` 的 `relative_luminance`/`contrast_ratio`/`legible_on`，在别的颜色
helper 旁边。
