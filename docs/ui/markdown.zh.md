# assistant 的 markdown 渲染

模型流式输出的是 **markdown**，但 assistant 的回复过去由 `ui::wrap_text` 当作
普通散文来折行，而它会把*连续空白压成一段*（那是给段落用的贪心折行）。这就毁掉
了唯一一种靠空白承载语义的结构：**围栏代码块**。一段 Python 代码被渲染成顶格、
缩进全无、各行还被重新折到一起 —— 根本没法读。

这是给 assistant 文本用的、前缀稳定的 markdown 层。它现在覆盖常见的全套结构 ——
与 codex / Claude Code 那种干净观感对齐：

- **围栏代码块与缩进代码块** —— 原样呈现（缩进逐字节保留）、语法高亮、围栏本身
  隐藏（见下文*代码* / *标题*）。
- **ATX 标题** —— `#` 标记**保留**，整行按层级上样式，跟 codex 一样；标记之后的
  文字按行内 markdown 解析，所以模型写的 `## **Title**` 会显示成 `## Title`
  （见*标题*）。
- **行内** `**bold**`、`*italic*`、`***both***`、`~~strike~~`、`` `code` ``、
  `[text](url)`、`![alt](url)`、`<url>` 自动链接、反斜杠转义与 HTML 实体，由
  CommonMark 的分隔符串算法解析（见*行内 markdown*）。
- **列表**按 codex 的观感 —— 每级圆点都是 `•`，任务项 `☐`/`☑`，有序项的 `N.`
  从列表起点重新编号，每层缩进四列，折行悬挂缩进 —— 以及能装下列表和标题的
  **引用块**（见*列表与引用块*和*块布局*）。
- **codex 的块间距** —— 块与块之间固定一空行，不管原文有没有；松列表被压紧；
  多行的一项与它的下一个兄弟隔开（见*块布局*）。
- **GFM 管道表格** —— 制表符画成的网格（见*表格*）。
- **分隔线**（`---` / `***` / `___`）画成一条 `———`。

贯穿全文的硬约束是**前缀稳定**（CLAUDE.md 不变量 2）：`StreamRender` 在回复
流式到达时就把它已经完成的行冲进终端真正的 scrollback，所以凡是渲染结果取决于
*之后*文字的结构，都必须**扣住**，等它定下来再放。**行内强调**需要这一点（一个
闭合标记可以给已经折好的行重新上样式），复用的是代码块引入的那套扣留机制
（`AssistantRenderer::in_code`）。**表格**需要为整块扣留（后面的一行可以重排每
一列的宽度，所以网格只在块闭合时渲染）—— 但条带会**实时预览整张正在成形的
表格**，因此它视觉上照样在流 —— 见 `docs/ui/table-streaming.md`。参见*前缀稳定
的扣留*。

## 它长什么样

````text
● ## The Code                                  ← `## **The Code**` → `#`s kept, `**` consumed
                                                ← one blank row between blocks
  Save this as snake.py:                        ← prose (word-wrapped, white)
                                                ← (inserted: codex sets a fence apart)
  def main(stdscr):                             ← code, verbatim, syntax-highlighted
      curses.curs_set(0)                        ← 4-space indent preserved
      while True:
          sh, sw = stdscr.getmaxyx()            ← 8-space indent preserved

  • Status: stable                              ← `- **Status:** stable` → `•`, bold label
  • Strengths: a long item that wraps onto      ← hanging indent under the text
    a second row
                                                ← AfterMultiline: a wrapped item is set apart
  • Key features: one row
      1. nested, four columns in                ← `  1. x` → codex's per-depth geometry
  ☑ shipped                                     ← `- [x] shipped`
````

## 标题（与 codex 对齐）

codex 的终端 markdown 渲染器（`codex-rs/tui/src/markdown_render.rs`、
`start_heading`）**不**剥掉 ATX 的 `#` 标记 —— 它把
`"#".repeat(level) + " "` 重新发成一个带样式的前缀，并用同一套样式给标题文字
上样式，所以一个标题看起来就是 **`## The Code`** 这样，井号仍然可见。各层级的
样式**只改文字修饰，不带前景色**：

| Level | Codex style       |
|-------|-------------------|
| `#`   | bold + underlined |
| `##`  | bold              |
| `###` | bold + italic     |
| `####`+ | italic          |

`ui::heading_style(level)` 是这套映射的直接移植，
`AssistantRenderer::heading_rows` 则在折行之前，把标题文字前面那段 `# ` 标记
（规整成一个空格，跟 codex 一样）重新拼出来。这是刻意**反转**了早先的行为
（丢掉 `#`，用 `ai_color()` 加粗），以便和 codex 完全一致 —— 读 codex 输出的
用户看到的是原始标记，那我们也把它们显示出来。

标题的**文字是行内 markdown**，跟在层级样式下解析任何散文行一样：codex 的
pulldown-cmark 那一趟对 `## **Bold title**` 产出的是 `Heading → Strong → Text`，
所以 `**` 被消耗掉，整行读作 `## Bold title`（层级的装扮与行内样式叠加 —— h3
仍然是粗体 + 斜体）。把标题当纯文本折行，就会把这些标记露出来 —— 这正是被报告
的那个 bug：模型给每个标题都套了 `**`。结尾的 `#` 序列（`## Title ##`）会被
丢掉，正如 CommonMark 所说。它仍然是一个纯粹的单行变换，而一个仍在生长中的标题
里的未闭合标记，会像其他情况一样被扣住（`has_open_inline`），所以前缀稳定性
以及批次/流式的一致性都没变。

代码就排在 assistant 圆点下面（与折行散文的缩进对齐，没有竖线），并由真正的
TextMate 语法**做语法高亮**（用当前主题自带的 syntect 主题 —— 默认 Catppuccin
Mocha，与 codex 对齐，其余每个 `/theme` 条目下都有对应的主题，见
`docs/ui/theme.md`；tag / 属性 / 选择器都着色，HTML 里内嵌的 CSS/JS 由它们自己
的语法高亮）。开头和结尾的 ` ``` ` 围栏都隐藏，info string 里的语言只用来挑
语法 —— 它**不会**作为标签显示出来。

**制表符在渲染路径上被展开成空格**（`expand_code_tabs`，固定替换成
`CODE_TAB_WIDTH` 个空格，跟 codex 的 `expand_tabs` 一样）。制表符占零个显示列
（unicode-width 把它当控制字符），所以用制表符缩进的代码 —— Go、Makefile ——
否则会缩进全失、顶格塌到左边。这个替换只影响显示：存下来的消息文本仍保留制表符，
所以 `/copy` 是逐字节精确的。它是一个在唯一的 `AssistantRenderer` 核心里应用的
纯单行变换，所以批量和流式保持一致，并且前缀稳定（一个制表符缩进的代码块就在
差分测试语料里）。

高亮是 codex 那套技术栈的移植（`highlight.rs`）：**`syntect`** 架在
**`two_face`** 的语法 + 主题包上（约 250 个 TextMate 语法）—— 和 codex 用的是
同一套东西（`codex-rs/tui/src/render/highlight.rs`）。它**替换**了早先手写的
一个通用 tokenizer，那个没有真正的 HTML/CSS 语法（它会把 CSS 的 `#id` 选择器
误判成 `#` 行注释，把标签渲染成纯文本）。我们用的是 syntect 的 **oniguruma**
正则引擎（`*-onig`），和 codex 一样 —— 这是 crate 里唯一一个 C 构建依赖
（`onig_sys` 打包并编译 oniguruma 的 C 源码，所以构建时需要 C 编译器）。这个
取舍是刻意做的：syntect 在首次使用某个语法时惰性编译它的正则，并缓存进共享的
`SyntaxSet`，而纯 Rust 的 `fancy-regex` 替代方案编译出来的这份状态要重得多 ——
实测**28 种语言下 fancy 占用 187 MB RSS，onig 约 23 MB**，降到 1/8。对一个模型
会写很多种语言的编程 TUI 来说，fancy 的占用正是这次修掉的内存增长 bug。语法的
scope 由主题解析成颜色（`convert_style`：前景色 + 粗体；斜体/下划线丢掉，与
codex 对齐），所以每个 `highlight::Seg` 现在带的是解析好的 `ratatui::Style` ——
这个 tokenizer **不再与颜色无关**（真正的语法能区分的，远多于一个固定六色
枚举），而 `ui` 什么也不映射。未知语言或 `text`/`console` 语言按纯文本渲染
（主题默认前景色）。

## 架构

- **`src/markdown.rs`** —— 一个纯粹的、有单元测试的模块（跟 `file_search` /
  `session` 一样）。`parse_blocks(text) -> Vec<Block>` 一趟走完文本，切成
  `Block::Prose(String)` 段和 `Block::Code { lang, lines }` 块；`fence_lang`
  取出 info string 里的语言（第一个 token）；`heading_level` 判断一个散文行
  是不是 ATX 标题。`BlockScanner` 是**增量**的对应物：
  `classify(line) -> LineKind` 一次一行地跑同一台围栏状态机（供 `StreamRender`
  用）。不碰终端，不做样式。
- **`src/highlight.rs`** —— 基于 syntect 的高亮器。`Highlighter::new(lang)` 把
  info string 解析成一个 `two_face` 语法（`find_syntax`，带 codex 的别名修补），
  并持有 syntect 的按行 `ParseState` + `HighlightState`；
  `Highlighter::line(text) -> Vec<Seg>` 解析一行源码（先补回语法所依赖的 `\n`，
  再剥掉），并把它的 scope 经主题解析成带样式的 `Seg`。状态会在多次调用之间
  带着多行结构（未闭合的字符串、注释、HTML→CSS→JS 的上下文），而 `Clone` 让
  `StreamRender` 能窥视一行进行中的代码。
  `highlight(lines, lang) -> Vec<Vec<Seg>>` 是个薄薄的批量包装。样式由主题烘
  进去（不归 `ui` 所有）；未知语言或纯文本语言每行产出一个纯 `Seg`
  （`plain_style` = 主题默认前景色）。语法库、主题和高亮器都是进程级
  `LazyLock` 单例，只构建一次。
- **`ui::AssistantRenderer`** —— 按行的渲染核心：`feed_line(line) -> Vec<Line>`
  经 `BlockScanner` 分类、经 `Highlighter` 高亮、折行，并盖上圆点（第一行）/
  缩进。**`ui::message_lines`**（每条已完成消息路径都走的批量漏斗 —— 流完再落定
  的 scrollback、resize 重绘、Ctrl+O 记录）和 **`ui::StreamRender`**（增量的
  流式提交器 + 预览）都驱动这一个核心，所以它们在构造上就渲染得*完全一致*。
  `message_lines` 把 `Role::Assistant` 走 `assistant_lines`（= 对
  `text.split('\n')` 驱动 `AssistantRenderer`）；**其他**每个角色走原来的纯文本
  路径，不变 —— 用户粘贴一个 ` ``` ` 永远不会被当成代码块，深色底的内边距计算也
  没被动过。

因为 `AssistantRenderer` 是唯一的那个核心，scrollback、流式预览、resize 重绘和
Ctrl+O 记录会自动一致（不变量 2–4）。

样式集中在 `ui/theme.rs` —— 代码的几何、列表字形（`LIST_BULLET`、
`LIST_TASK_OPEN`/`LIST_TASK_DONE`、`LIST_NEST_WIDTH`），以及颜色取值函数；标题
样式只改修饰（`heading_style`）。代码在 `content_width` 处强行断行，而不是交给
终端去折 —— 否则一行比终端宽的代码会被模拟器在错误的列上折掉，圆点下的对齐就
没了。

## 流式过程中的增量渲染（`ui::StreamRender`）

`message_lines` 是从零渲染一条**已完成**的消息 —— 对 resize 重绘和 Ctrl+O 记录
来说没问题（一条消息，只渲染一次）。但一条*流式中*的回复，在**每一条**按 chunk、
按帧运行的路径上也被整条渲染：`stable_commit` 把累积的整条回复重渲一遍，只为
找出新稳定下来的行；条带预览又重渲一遍，只为拿最后一行。每次都是 O(回复长度)；
一段分 ~N 个 chunk 到达的流，整体就是 **O(回复长度²)**，而这全跑在单线程的事件
循环上。一条长的代码回复实测在 1200–1600 行时**每动画帧**约 30–40 ms —— 超过了
32 ms 的状态帧预算 —— 于是 spinner 肉眼可见地卡顿，输入也迟滞。（测量见
`examples/perf_probe.rs`，以及这次改动的 git 历史。）

`ui::StreamRender` 的解法是**增量**渲染。它驱动同一个 `AssistantRenderer` —— 从
`assistant_lines` 里抽出来的按行核心，所以批量和流式渲染得*完全一致* —— 通过
`markdown::BlockScanner`（增量的围栏状态机，`parse_blocks` 的对应物）和
`highlight::Highlighter`（增量的按行高亮器，`highlight` 的对应物）喂给它源码行。
它**缓存**每个完整源码行渲染出的行，并在每次 `commit`/`preview` 时只前进到上次
调用之后新到的那些行。于是一次 `commit` 是 O(新文本)，一次 `preview` 是
O(一行)：把整条回复流完是 **O(回复长度)**，而每帧重绘预览几乎不要钱。（唯一残留
的情况是一个内部没有换行的单行源码 —— 一个长段落，或压缩成一行的代码：它仍在
生长的*末行*每次调用都要重新折行，所以每次 commit/帧是 O(行)。这被一行封顶，
对同样的输入并不比旧的整条重渲更差；真实回复里有换行，所以实践中碰不到。）

边界（`main.rs`）为每个回合持有一个 `StreamRender`（取代原先的
`committed: usize`）：每个 `Chunk` 上 `commit`，在 `StreamDone`/工具切分/中断
时 `finish`，每次绘制前 `preview`（它给出的那一行交给
`ui::render_live_with_preview`），并在每个回合边界（回合结束、工具切分、中断、
`/clear`）**以及每次 purge 重建之前** `reset`（resize、`/clear`、历史回退 ——
purge 把已提交的每一行都清掉了，所以随后的 commit 要在新宽度下重新发出整条
回复）。流中途的**overlay 返回**完全不动它：overlay 弹着的时候 `Chunk` 分支
照旧提交 —— 行只是在 viewport 上排队 —— 返回时的那次绘制会把它们冲出去，所以
恢复后的屏幕保留已经流过的部分，而 overlay 期间的增量恰好落一次（只凭历史重绘
会把部分内容抹掉，直到下一个 chunk —— 就是 Ctrl+O 那个先消失再闪的 bug；
`smoke.sh` 第 35 和 82 阶段）。

## 流式时为什么安全（前缀稳定）

`StreamRender` 在回复流式到达时，把每条已完成的回复行冲进终端真正的 scrollback，
只扣住**最后**一行渲染结果（CLAUDE.md 不变量 2）。这只有在渲染是*前缀稳定*时
才成立：往回复后面追加只可能改变最后产出的那一行；之前每一行都永久冻结。因为
`StreamRender` 缓存了一行已完成的渲染行、从不回头看，前缀稳定*在构造上*成立 ——
但前提是每一行的渲染行确实不依赖它之后的任何东西：

代码块（包括它们的**语法颜色**）和标题满足这一点，因为它们的渲染是每行之前那段
文本的、纯粹从左到右的函数：

- 一行的散文/代码**模式**由进入它时的围栏状态决定 —— 那是对它前面各行的扫描，
  不看后面。追加永远不会给*更早*的行重新分类。一个**未闭合**的围栏渲染成代码的
  样子和一个已闭合的**完全一样**，所以等到闭合的 ` ``` ` 终于到达时，什么都不会
  变（它只是产出零行）。唯一的例外是*围栏开头那一行本身*：当它还是个**残缺**的
  标记序列（`` ` `` 或 `` `` ``）时按散文渲染，第三个标记到达时翻成**零行**
  （围栏被隐藏）—— 这是行内的重新分类。在正常宽度下，这段 1–2 列的散文是单独
  一个（被扣住的）末行，但在内容宽度 1 时它会折成两行，所以
  `StreamRender::commit` 在 `markdown::is_partial_fence` 成立时也扣住末行 ——
  于是不变量在*每个*宽度下都成立（差分测试覆盖宽度 3 及以上）。
- `wrap_verbatim` 的宽度硬断行是贪心的、逐个字素进行的，所以追加只会延长或
  新起*最后*一行 —— 与 `wrap_text` 完全一致。
- 标题的样式触发器（行首的 `#…`）在该行任何输出行被提交之前就已经看到了。
- 语法颜色是按行的：一行的 token 是它自己文本加上进入它时的多行 `Carry`（未闭合
  的三引号字符串 / 块注释）的纯函数 —— 而 `Carry` 本身是对之前各行的从左到右
  扫描。一个未闭合的三引号字符串或 `/* … */` 会把余下部分染成字符串/注释，与已
  闭合时完全一样，所以已提交的代码行永远不会被重新上色。
- **但高亮用到了行内的一字符前瞻**（标识符在 `(` 处变成调用，`/` 在下一个 `/`
  处变成注释）。一行比宽度更长的代码会折成好几行，在前瞻字符流入之前就提交靠前
  的行，会把它的颜色改掉。所以 `StreamRender::commit` 只要末行位于围栏块之内
  （`AssistantRenderer::in_code` —— 有一道围栏开着时 `Highlighter` 才存在），就
  扣住**进行中的代码行**。散文没有这种前瞻，仍然按折好的行流式输出。这是代码
  唯一需要按源码行设闸的地方 —— 也是行内强调到处都需要的那套机制。

### 末尾空行会被裁掉

模型经常在调用工具之前，用一个段落分隔（`…\n\n`）结束 assistant 消息。那些末尾
的空源码行会渲染成空行，而边界本来就已经在消息和工具单元格之间插了**一个**间隔，
所以不裁的话它们会叠成三个空行（一个被报告的 bug）。现在两条渲染路径都会丢掉
一条消息的**末尾**空行：批量的 `assistant_lines` 在渲染后把它们弹出，流式的
`StreamRender` 则在 `commit` 里**扣住**它们（它们只有在真正的内容跟上时才提交，
所以绝不会成为已提交行的回归），并在 `finish` 里裁掉。中间的空行（两个段落*之间*
的段落分隔）不受影响，而且这个裁剪受 `!in_code()` 约束，所以开着的围栏里的空行
—— 那是内容 —— 会留下来。`preview` 同样跳过末尾空行（检查的是*末尾行之后*的
围栏状态，因为末尾的 `` ``` `` 会打开一道围栏，并把它前面的空行留住），所以条带
的最后一行与裁剪后的批量渲染一致。一段只有空白的片段根本不会记下消息
（`App::flush_streaming_segment`/`finish_stream`），所以重绘无法让一个实时视图
从没显示过的、孤零零的 `●` 圆点复活。
`stream_render_matches_batch_render_on_every_prefix` 用带末尾 `\n\n` 的语料
条目覆盖了这一点。

`ui::tests::stream_render_is_prefix_stable_over_every_prefix` 对一条散文回复和
一条围栏代码回复的*每一个*字符前缀驱动 `StreamRender`，并断言已提交的行在文本
**和颜色**上都从不改变；
`ui::tests::streamed_code_never_recolours_a_committed_row` 钉住了调用 `(` 那个
具体的重新上色场景（正是它第一次暴露出需要 `in_code` 闸门）；而
`ui::tests::incremental_commits_reconstruct_a_fenced_code_reply` 证明流式提交
加上最后一次冲刷等于完整渲染出的消息。
`markdown::tests::block_scanner_agrees_with_parse_blocks_on_code_membership` 和
`highlight::tests::incremental_line_by_line_equals_batch_highlight` 把增量扫描器
锁死在它们的批量对应物上。

## 范围（以及刻意排除的东西）

**在内：** 围栏代码块（` ``` ` 与 `~~~`，原样）、**缩进（4 空格）代码块**、ATX
标题，以及**分隔线**（`---` / `***` / `___`）。

按 CommonMark，*反引号*围栏的 info string 里不能含反引号 —— 这样一行
（`` ```rust`x ``）是行内代码散文，不是开头（若当成开头，会把回复的其余部分吞成
一个未闭合的块）；波浪号围栏则可以。一个**前导制表符**（缩进 ≥4 列）会让一行
本应是 `---` 的内容变成缩进代码，永远不是分隔线。而在流式过程中，末尾一段
**光秃的 `#`**（1–6 个井号）会像残缺围栏一样被扣住
（`markdown::is_partial_heading`）：它的标题*层级* —— 因此它的粗体/斜体样式 ——
要等到空格、文字，或第 7 个 `#`（那会把它翻成散文）到达才定下来，所以在比这段
更窄的宽度下，它折出的行还不能进入 scrollback。

**在内 —— 缩进（4 空格）代码块。** 一段每行都缩进 ≥4 空格（或以制表符开头）的
连续行，是 CommonMark 的缩进代码块，跟围栏块一样**原样**渲染（纯文本，没有
语言）。它只在空行之后或文本开头才开始（`markdown::BlockScanner` /
`parse_blocks` 里的 `prev_blank`），所以它绝不会把一段懒续行的段落误判成代码 ——
与 codex 的 `CodeBlockKind::Indented` 一致（后者剥掉 4 空格标记再补回 4 空格
前缀；净效果 = 源码缩进，我们保留的正是这个）。这段里的空行仍属于它。有一项
豁免：一行如果被解析成**列表项**（`markdown::list_item` —— 任意空格缩进下的
`- `/`N. ` 标记），就永远不*开启*缩进块 —— 空行之后一行 4 空格标记是松列表的
**嵌套项**，顶层缩进规则否则会把它吞掉（CommonMark 的规则是依上下文而定的；
只看本行的话，标记本身是更好的证据）。一个看起来像标记的行，若*位于*已经开着的
块内部，仍然延续该块，所以包含 `- x` 这类行的真实代码保持完整。在列表项内部，
规则越过该项自身的缩进来适用（扫描器收到的行已剥掉容器前缀，见*块布局*），所以
`1. ` 下缩进 4 空格的段落是该项的文字，不是代码。这是前缀稳定的（一行是否属于
该块只取决于它之前的行）且是纯文本的（没有高亮器 → 没有行内前瞻），所以它的
已完成行像散文一样逐行流进 scrollback。

**在内 —— 分隔线。** 一行 `---` / `***` / `___`（CommonMark 的分隔线语法 ——
`markdown::thematic_break`）会渲染成 codex 那条不带样式的 `———` 破折线
（`Event::Rule`、`ui::THEMATIC_BREAK`），两侧各留一空行。`-` 分隔线**紧跟在
段落行之后**也会渲染，而 CommonMark 会把那段读成 setext `H2` 的下划线：在模型
的回复里，这种形状是一个丢了空行的分隔符，不是标题，而 setext 读法需要下一行的
前瞻，流式给不起 —— 所以旧渲染器把 `---` 当散文露出来的地方，现在画的是分隔线。
流式过程中，末尾的分隔线序列 —— 无论是残缺的（`--`、`**`）还是完整的
（`---`，`--- x` 会把它变回散文）—— 都会先扣住不进 scrollback，直到该行定下来
（`markdown::has_unsettled_block_prefix`，见*前缀稳定的扣留*）。

**在内 —— 行内 markdown。** `markdown::parse_inline` 把一行散文变成一棵
`Inline` 节点树（`Text`、`Bold`、`Italic`、`Strike`、`Code`、`Link`、`Image`、
`Url` —— 嵌套会叠加，例如 `**bold _and italic_**`）；`ui::inline_spans` 把每个
节点映射成 `Style`（强调只改修饰；代码是青色；链接先显示文字，然后是一个蓝色带
下划线的 ` (url)`；自动链接用它赤裸的 URL 配上链接的装扮；图片渲染它的 alt），
而 `ui::wrap_inline` 对带样式的片段做**保形**折行（一段粗体跨过折行边界仍保持
它的样式；被强调拆开的单词 —— `un**bold**` —— 仍是一个词）。

强调遵循 **CommonMark 的分隔符串算法** —— 也就是 codex 的 pulldown-cmark 那一趟
所做的解析。每个 `*`/`_` 串（以及 `~~` 对）按左/右侧翼规则分类（`_` 在单词内部
从不开启或闭合，所以 `snake_case` 和 `2 * 3` 保持字面），然后闭合符从左到右，
在「三之规则」下取最近一个兼容的开启符，它们之间的片段成为一个节点。这正是修掉
旧的「最长标记优先」匹配器那些漏判的地方：`***x***` 是粗体中套斜体（以前会
显示成粗体的 `*x*`），一个闭合的 `***` 在它闭合的两个开启符之间拆开
（`**x *y***`），而更长一串里剩下的标记保持字面（`**x*` → `*` + *x*）。
`openers_bottom` 记住一次搜索空手而归回溯到了多远，所以一行没配上的标记仍是
线性的（`parse_inline_stays_linear_on_a_line_of_unmatched_markers`）。链接和
图片的方括号也这样配对：`Brackets` 用一趟栈扫描，一次配对完一行的 `[`/`]` 与
`(`/`)`，每个开启符都去那里找它的闭合符 —— 每个开启符各扫一遍，会让一行未闭合
的 `![`、`[` 或 `[a](b` 变成平方级（一个 25 KB 的曾要 1.6 s 才解析完，现在约
10 ms；`parse_inline_stays_linear_on_a_line_of_unclosed_brackets`）。有一处
放宽：CJK 文字词间不加空格，所以一个外邻是 CJK 字符的标记串，在那一侧不受标点
条款约束 —— `**标题：**内容` 仍然渲染成粗体，而严格的 CommonMark（以及 codex）
会把标记露在外面。

tokenizer 还解析**反斜杠转义**（`\*` 显示为 `*`，且永远不是分隔符；除 ASCII
标点之外的字符前的反斜杠保留）、**自动链接**（`<https://…>` 与
`<me@example.com>`，显示时去掉尖括号）、**链接标题**（`[a](url "title")` 链到
`url`），以及常见的 **HTML 实体**（`&amp;`、`&nbsp;`、`&#169;`、`&#x2014;`、…
—— 未知的名字保持字面）。代码 span 保留它们的反斜杠，如 CommonMark 所说；而
表格单元格把除 `\|` 之外的每个转义都交给这个解析器，所以单元格里的 `\*x\*`
保持字面。它是**行内局部**的 —— 未闭合的标记保持字面 —— 所以一个*完整*行的
样式是最终的（它冻结的行永远不会重新上样式）。末行的情况见*前缀稳定的扣留*。

**在内 —— 列表与引用块。** `markdown::list_item` 分类一个圆点项
（`-`/`*`/`+`，保留它的字符）或有序项（`N.`/`N)`）—— 缩进、标记、内容 —— 而
`markdown::block_quote` 剥掉一个 `>`，检查顺序在 `thematic_break` *之后*，所以
`- - -` / `* * *` 仍是分隔线。渲染器把两者都当作后续行可以延续的**容器**（见
*块布局*），并按 codex 的方式画它们：

- **圆点**在每一层都渲染成 `•`，不管模型写的是 `-`/`*`/`+` 中的哪一个
  （`ui::LIST_BULLET`）；源码里的 `-` 从不出现。
- **有序项**把 `N.` 用强调色渲染（`list_marker_color`），`N)` 规整成 `N.`，
  并按 codex 的计数方式**从列表起点重新编号**：`1.`、`1.`、`1.` 读作 1、2、3，
  而写成 `3.`、`4.` 的列表保留 3 和 4。另一种类型的项 —— 不同的圆点字符或
  分隔符，或圆点之后的有序项 —— 会开启一个新列表（CommonMark）。
- **任务项**（`- [ ]`、`- [x]`、`- [X]`）把圆点换成 `☐`/`☑`（有序项保留它的
  编号：`1. ☑`）。方框后面需要空白 —— 光秃的 `- [x]` 保持字面，codex 也是这么
  留的 —— 而方框之后是该项的文字，绝不会又是一个标记（`markdown::task_box`）。
- **嵌套**遵循 codex 的几何，而不是源码的：每层深 `LIST_NEST_WIDTH`（4）列 ——
  有序编号在那个内边距里右对齐 —— 不管模型是缩进 2、3 还是 4 空格，还是用制表符
  （见*块布局*：行前缀里的制表符计到下一个四列停位）。续行悬挂在项的文字下面。
- **缩进短于某项文字、但起点超过该项标记两列以上的一块**仍然嵌套：模型会在
  `1. ` 下两空格写子列表，在 `10. ` 下两到三空格，CommonMark —— 以及 codex ——
  会把它读成另一个列表，把它压平并重排父列表的编号。放在那里的列表项、围栏、
  引用、标题或表格仍留在项内；只进去一列的，是写得潦草的兄弟项（`1. a` 之后的
  ` 2. b` 继续计数），而段落文字仍需要到文字列，否则就按懒续行处理。
- **项下的文字** —— 一条缩进的续行、一条*懒*续行（不缩进，前面没有空行：
  CommonMark 把它留在项的段落里）、空行之后的第二个段落、缩进到项内容列的一道
  围栏或一个引用 —— 都渲染在项的文字下面。`1. ` 下缩进 4 空格的段落是该项的
  文字，不是缩进代码，而嵌在二级项下的一道围栏仍然是围栏（这两者以前都会坏：
  代码色的散文，以及屏幕上露出来的反引号）。
- **引用块**给每一行加上绿色的 `> ` 前缀（嵌套引用重复它），铺在绿色文字上 ——
  codex 的引用装扮（`blockquote: Style::new().green()`），即主题的 `success`
  角色，行内代码和链接保持自己的颜色 —— 而它们的内容也是 markdown：`> - a` 是
  引用里的圆点，`> ## Note` 是标题，空 `>` 行分隔段落，懒续行延续被引的段落。

**在内 —— GFM 管道表格。** 一个表头行、一个**分隔**行（`|---|:-:|`，它的列数
与对齐方式决定网格），以及数据行，渲染成制表符画出的网格（暗淡的边框、粗体表头
单元格、逐列对齐，每行之间有 `├──┼──┤` 隔线 —— Claude Code 的完整网格）。两处
细节补全这种观感：当分隔行没有声明对齐时，**表头单元格**在自己的列里**居中**
（`ui::header_align` —— 声明过的 `:--`/`:-:`/`--:` 仍然优先，所以明示的意图得以
保留）；而单元格比它所在的行矮时**垂直居中**，所以一行的值会坐在折成三行的邻居
的中间行，而不是贴着它的顶边。整块是**整体缓冲**的，闭合时才渲染，列宽按表头
**以及每一个数据行**拟合 —— 所以后面一个更宽的行永远无法把网格撑碎。当自然网格
溢出宽度时，每列先按它最长**单词**所需的宽度落座，余量按未满足的需求分配
（`allocate_column_widths`），于是内容确实长的列拿到空间，而不是每列都被拉平到
同样大小；只有连这些下限都放不下时，才退回到压缩最宽的那列。单元格**折行**进
分配到的宽度（行变高），而不是用 `…` 截断。一个**被硬折的行** —— 源码在行中间
带了换行，于是带管道符的片段行（`96.4 ms |`）跟在它那个前导管道的行后面 —— 会
**重新并回**它从那里折出来的行，而不是凭空造出一个只有一格的幽灵行
（`ui::join_wrapped_table_row`，见
`docs/ui/table-streaming.md`）。块开着的时候，
条带**预览整张正在成形的表格**（每帧重渲，随着行到达重新拟合列宽），所以表格
视觉上仍然从头流到尾。闭合时它还要决定用网格还是**键/值记录**：当网格挤到没法
扫读时（列被压得太窄），每行改为渲染成一个 Claude Code 风格的竖排
`label: value` 块（行之间一条收窄的 `─` 分隔线）—— 绝不用 `…`。见
`docs/ui/table-streaming.md`（状态机、宽度分配、记录回退，以及多行预览）—— 它
替换了原先「在第一个数据行锁死宽度」的流式做法，那种猜出来的宽度会把后面任何
更宽的行折成碎条（被报告的那个 issue）。

**单元格内容是行内解析的** —— 单元格里的 `` `code` ``、`**bold**`、
`*italic*`、`~~strike~~`、`[text](url)` 等会像散文一样带样式渲染（与 codex
对齐），而不是显示成字面标记（`ui::table_cell_segments` =
`inline_spans(parse_inline(cell))`）。因为标记被剥掉，列是按单元格的**渲染后**
显示宽度来定尺寸的（`segments_cols`，所以 `` `foo.db` `` 量出 `foo.db` = 6，
不是 8），而 `table_row_lines` 对每个带样式的片段按对齐方式折行 + 补边
（`pad_cell_line`）—— 也就是旧的 `pad_table_cell` 用纯字符串量尺寸的、保样式的
对应物。表头单元格带一个**粗体**基础样式，行内样式叠加在它之上。批处理
（`assistant_lines`）和流式驱动的是同一个 `AssistantRenderer`，所以它们渲染得
完全一致（一个单元格里有行内 markdown 的表格就在差分测试语料里，宽度 3–40）。
*检测*仍然要求行形状符合 `markdown::is_table_row`/`table_delimiter` 的判据
（分隔行必须含一个管道符）；一张没有管道符的 GFM 表格会按散文渲染，这次改动
没有改变这一点。

**语法高亮是语法精确的（`syntect` + `two_face`）。** 用的是真正的 TextMate
语法，所以每种语言的形状（多行字符串/注释、字符串插值、HTML 里像 CSS/JS 这样
的内嵌语言）由语法本身处理，并借助 syntect 的 `ParseState` 跨行携带。未知语言
或 `text`/`console` 语言按纯文本渲染（主题默认前景色）。进行中的代码行仍然扣住
不进 scrollback，直到它完成（`AssistantRenderer::in_code`），因为语法是一次
解析整行的（后面到达的字符可能改变 scope）—— 只有已完成的行才提交；见上文
*流式*那一段。护栏：单行超过 4 KB（一坨压缩过的 bundle 被粘进围栏）就干脆不
高亮，而不交给正则引擎 —— 这个上限是**帧预算**，不只是安全网：当这样一行是流式
回复的末行时，条带预览会在每个带新 chunk 到来的帧上重新高亮它，而一行 62 KB 的
压缩 JSON 实测每趟 oniguruma 超过 150 ms。编辑器也这样给 tokenization 设上限；
超过上限后该行用纯代码样式渲染，文本逐字节不变。

## 块布局（codex 的列表、引用与间距）

codex 经由 pulldown-cmark 渲染，所以它对一条回复的图景是一棵树：块在列表项里，
列表项在引用里。我们的实现一次渲染一行源码，所以渲染器携带那棵树里「一行还可能
加入」的那部分 —— `AssistantRenderer` 的**容器栈** —— 并像 CommonMark 的块解析
器那样读每一行：

1. **延续已开的容器**，从最外层开始：引用需要一个 `>`（消耗它的标记和一个
   空格），列表项需要一个空行，或一行缩进到该项内容列的（消耗该缩进）—— 或者
   一个起点超过该项标记两列以上的块（列表项、围栏、引用、标题或表格），消耗它
   的全部缩进，模型就是这样在 `1. ` 下嵌套的（*在内 —— 列表与引用块*）；延续
   一张开着的表格的行也这样跟随表格的缩进，有没有管道符都一样。剩下的就是该行
   相对于匹配到的最内层容器的部分。在这一切之前，该行的**块前缀** —— 它的
   缩进，以及它 `>` 和列表标记之后的空白 —— 的制表符先展开到 CommonMark 的四列
   停位（`markdown::expand_prefix_tabs`），所以 `\t- child` 的嵌套与
   `    - child` 相同，而不是把它的 `-` 露出来；前缀之后的制表符是内容。
2. **懒续行。** 一行若没延续上每个容器，但紧跟在段落行之后、是段落文字（中间
   没有空行），它就是*懒续行*：所有容器保持开着，它延续那个段落 —— `- item`
   之后一个不缩进的 `more` 是该项的文字，`> a` 之后一个 `b` 是引用的文字。其余
   情况按从内到外的顺序关掉没匹配上的容器。
3. **开启新容器**：剩下的部分若以引用或列表项开头，能装多少就开多少
   （`> - x`、`- > x`）。
4. **渲染叶子** —— 剩下的部分：一道围栏、缩进代码、一个标题、一条分隔线、一个
   表头，或一行段落 —— 并给它们加上容器的前缀。

每个作用域 —— 消息、每个引用、每一项 —— 都记住自己的**上一个块**，而这正是
codex 的间距所需要的全部：

- 同一作用域里，新的块与它前一个块之间空出**一个空行** —— 标题与它的正文、
  列表与引出它的那段话、围栏与它周围的散文 —— 不管源码原来有没有：缺的空行会
  补上，一串空行会并成一个。空行从不按原位渲染；它只结束一个段落
  （`pending_blank`），由下一个块发出分隔符。分隔符从不叠在已经存在的空行上
  （代码块自己末尾的空行），而一道围栏的分隔符会一直欠着，直到它的第一行代码
  （`fence_gap`），所以一道空的围栏在回复暂停时不会留下多余的行。
- **软换行** —— 紧跟在段落行之后的一行文字 —— 是一个没有分隔符的新行，即 codex
  的 `soft_break`。
- **列表**遵循 codex 的 AfterMultiline 规则：源码里两项之间的空行被丢掉（松
  列表被压紧），而一行数 —— 折行的文字、嵌套项、续接段落、代码 —— 超过一的行，
  会与它的**下一个兄弟**之间空一行。嵌套列表紧贴父项；顶层列表像其他块一样被
  隔开。
- 在 codex 里，**紧凑项的文字从不结束段落**，所以让标题、引用或表格被隔开的
  `needs_newline` 在那里从不触发：紧贴该项文字、中间没有空行的这类块会贴上去
  （`separator_unless_tight`），而围栏和分隔线仍保留 codex 一贯给它们的间隙。
  空行会让该项变松，分隔符就回来了。
- 在引用内部，分隔符保持引用的 `> ` 那一列不断开。

一行所戴的前缀按 codex 的方式叠加容器：每个引用加 `> `；两个引用之间的诸项里，
只有最内层说话 —— 它的标记在它的第一行，它的悬挂在之后 —— 因为嵌套的标记本身
已经带着它深度的内边距。**围栏**块在 CommonMark 严格的地方放宽：一行代码会剥掉
引用存在时的 `>`，以及最多到某项缩进的列数，所以模型在项的围栏里缩进不足时，
得到的仍是代码，而不是一道撕裂成散文的围栏。然后，正如 CommonMark 所说，它再
丢掉最多**围栏自身的缩进**（`fence_indent`），所以缩进两空格的围栏，代码留在
围栏所在的地方，而不是右移两列 —— 而一道宽松延续下来的项的围栏只剥掉它在那里
消耗的部分（`fence_lenient`），于是代码保留它写成时的缩进。这些剥除都把制表符
计到它的停位，并把代码自己的制表符留给 `expand_code_tabs`。

**为什么它保持前缀稳定。** 一行渲染出的每一行 —— 包括它前面的分隔符 —— 都只
依赖它之前的行（栈、各作用域的上一个块、待处理的空行、上一项的行数）以及它
自己。分隔符是*和开启下一个块的那一行一起*发出的，绝不在它跟随的块之后，所以
已经提交的东西永远不会被改写。一行还在流的时候可能变的，是它的**块前缀** ——
`1.` 是会变成列表项（`1. x`）还是散文（`1.5`），`- 1` 是嵌套列表，`---` 是
分隔线而 `--- x` 是散文 —— 提交器会在它定下来之前扣住
（`markdown::has_unsettled_block_prefix`，见下文）。差分测试的语料覆盖了这里
每一条规则在每个前缀、每个宽度下的情形，而模糊测试器的汤里也长出了容器相关的
碎片（被引用的项、任务方框、懒续行与续接行、光秃的标记、缩进短于项文字的块、
制表符缩进的项与围栏）。

## 前缀稳定的扣留（表格 + 行内强调）

`StreamRender` 在回复流式到达时就把它已完成的行冲进真正的 scrollback，所以凡是
渲染结果取决于*之后*文字的东西，都必须**扣住**，等它定下来再放。行内强调和表格
都需要这一点，复用的是代码块的扣留机制（`AssistantRenderer::in_code`，
`StreamRender::commit` 已经在用它把进行中的*代码*行挡在 scrollback 之外）：

- **表格 —— 缓冲整块，整块预览（`docs/ui/table-streaming.md`）。**
  `AssistantRenderer` 把整块缓冲起来（`PendingHeader` → `Buffering`，
  **不产出任何行**）；`in_table()` 报告任何开着的表格，而
  `StreamRender::commit` 在它成立期间扣住末行（另外还扣住一个末尾的
  **表头候选**，`markdown::is_table_header_candidate(tail_src)`，在渲染器消耗
  它之前）。一块只在带**前导管道符**的表头上*开启*：GFM 那种前导管道符可省
  （无表头）的形式与流式不兼容 —— 任何正在生长的散文行，都可能在后面的 `|`
  流进来的那一刻变成表头（`` `span`a `` → `` `span`a | b `` 加上下一行的分隔
  行），把已经冻进 scrollback 的行追溯性地重画成网格 —— 所以表头资格在该行的
  第一个字符处就决定，普通散文渐进提交，而少见的无表头表格在批量和流式里一样
  按散文渲染。已确认表格*内部*的数据行仍用宽松的 `is_table_row`（包含被硬折的
  尾巴的重新并回）。因为缓冲状态什么都不产出，任何表格行都不可能在块闭合之前
  提交 —— 而闭合时它整块渲染，列宽按**每一行**拟合。同时条带的 `preview` 显示
  整张正在成形的表格（批量渲染的未提交尾部 —— 一个多行预览），所以表格在视觉
  上照样在流。批量（`assistant_lines`）和流式驱动同一个
  `AssistantRenderer`，所以它们渲染一致。
- **行内强调 —— 按行换行设闸。** 因为强调是行内局部的，一个*完整*行总是最终
  的；只有**末尾那半截**行可能重新上样式（一个开着的 `**` 还可能闭合）。
  `markdown::has_open_inline` 报告末行上未闭合的强调/代码/链接分隔符，而
  `StreamRender::commit` 在它成立期间扣住整行 —— 于是一段在途的 `**bold`
  永远不会半上样式地进入 scrollback。等它定下来（闭合符到达，或该行结束时标记
  保持字面），它才提交。位于生长中那行**最末**的标记是*未定*而非已定 —— 它
  算不算侧翼由下一个字符说了算（`~~` + `s` 藏起波浪号并给后面的内容加删除线，
  `~~` + 空格则让它们保持字面），末尾一个 `!` 若下一个字符是 `[` 就成了图片
  开启符，而末尾一个反引号可能是下一字符会**延长**的闭合串（`` `x` `` +
  `` ` `` → `` `x`` `` 打破了精确串匹配，看着已定下来的 span 又退回字面）——
  所以 `has_open_inline` 也会标记以 `*`/`_`/`~`/`!`/`` ` `` 结尾的行。
- **赤裸的 URL —— 自动链接的扣留（`docs/ui/links.md`）。** URL 检测是追溯性地
  打开或关闭的（`ht` 是散文，`http://e` 是链接 —— 整个词重新染成蓝色 +
  下划线），而一个伸到行尾的 URL 正文还在生长（它末尾被裁掉的标点可能再并回
  来：`http://e.` → `http://e.com`）。`links::has_forming_url` 报告这两种
  形状，而 `StreamRender::commit` 在其中一种成立时扣住末行。

块级的扣留是一个谓词，**`markdown::has_unsettled_block_prefix`**：一个末行，
其块前缀还可能被下一个字符改变，在最顶层检查，*也在该行已持有的 `>` 和列表
标记背后检查*（`> -`、`- 1`、`> > ##`）—— 一道残缺围栏（`` ` ``/`` `` ``）、
一段分隔线（`--`、`**`，甚至完整的 `---`）、一段光秃的 `#`（它的层级、因而它
的样式都未定），或者一个后面什么都没有的列表标记（`is_partial_list_marker`：
一串数字、`1.`、`2)`，或孤零零的 `-`/`*`/`+` —— 一个空格让它成为列表项，一个
带自己间距和缩进的容器，其他任何东西则是散文）。任务方框结束这次下降：它后面
的是该项的文字。它用渲染器所用的同一个 `expand_prefix_tabs` 读这一行，所以
制表符缩进的 `\t-` 像 `    -` 一样被扣住。行内的扣留 `has_open_inline`（见
上文）也覆盖了新的行内形式 —— 分隔符串算法之后没配上的开启符、仍在成形的自动
链接或实体，以及末尾的 `\`、`<` 或 `&`。

**CRLF 回复渲染得和它们的 LF 孪生一样。** 一个回显 Windows 文件的模型（或一个
把内容规整成 CRLF 的 provider）流出的是 `\r\n` 行尾；源码只按 `\n` 切分，所以
每行到达时都以 `\r` 结尾。`AssistantRenderer::content_rows` 剥掉那一个尾部
CR —— 它属于行尾，不是内容 —— 于是围栏、分隔线和表格的分类与它们的 LF 孪生
完全一样（`---\r` 以前会渲染成字面散文），也没有任何代码行会把多余的 CR 带进
scrollback 或一次 `/copy`。*行中*的 CR 保留：它是内容（散文把它当空白压掉，
绘制层丢零宽字形）。批量和流式共用同一个入口，所以两者从不会不一致。

差分测试 `ui::tests::stream_render_matches_batch_render_on_every_prefix` 在
一个大语料（表格、行内强调、嵌套列表、引用块、链接、任务列表、标记显隐翻转）
的**每一个字符前缀**上驱动 `StreamRender`，宽度 3–40，并断言已提交的行始终是
批量渲染的稳定前缀、最后一次冲刷能精确重建它、而预览是批量渲染的一个**后缀**
—— 整段未提交的尾部，所以 `committed + preview` 覆盖整个渲染结果。它是这里
每种结构的护栏 —— 动渲染器时要扩展它，绝不削弱它。它那个对抗性的兄弟
`ui::tests::stream_stress` 用带种子的 PRNG 在**生成的**敌意碎片汤上模糊测试
同样的不变量（未闭合标记、围栏/表格碎片、CRLF 拼接、控制字符与 ANSI 转义、
零宽/BiDi 码点、emoji/CJK、正在成形的 URL、setext 下划线、被转义的标记、
尖括号自动链接、引用式链接、嵌套引用、孤立的 ZWJ、叠在一起的组合标记、代码
span 里的管道符、混用的制表符缩进），所以连手写语料没想到的组合仍然被机器检查
—— 行尾标记、成形 URL、无表头表格和围栏末尾空行那几处扣留，全都是模糊测试找
出来的。

它还覆盖了实时屏幕断言看不到的路径。**purge 重建**：一次 resize、`/clear` 或
历史回退会从 `committed_rows` 重渲 scrollback，同时条带在旁边重绘，所以
`committed_rows ++ preview` 也必须等于批量渲染
（`a_purge_rebuild_plus_the_strip_still_shows_the_whole_reply`）；流中途改宽度
必须仍能在新宽度下重建回复
（`a_mid_stream_width_change_reconstructs_the_reply`）；而 0 或 1 列的屏幕 ——
动画进行中的平铺窗口管理器 —— 不能让一次绘制 panic
（`a_degenerate_terminal_width_is_survivable`）。

它还带着体量约束。一条 250 KB 的代码回复和一条 130 KB 的单行回复必须以线性
时间流完（`commit` 的摊还器 + `advance` 的换行高水位 + `StreamRender` 里
`preview` 的备忘），一次对超长代码行的 `preview` 必须停在一帧预算之内（4 KB
高亮上限），而摊还器绝不能把行藏在屏幕之外 —— 它推迟的提交仍在条带里可见，
正是这一点让推迟是安全的
（`the_commit_amortizer_never_hides_rows_from_the_screen`）。
有一个**已知的线性上界**是用测试钉住的，而不是想办法消掉的
（`the_strip_redraw_stays_inside_a_frame_on_a_huge_prose_line`）：一行超长的
*散文*没有 syntect 上限那样的对应物，所以每个落到新 chunk 上的帧都要通过
`parse_inline`/`wrap_inline` 重渲它 —— 在 130 KB 下实测每帧约 6 ms，而节奏是
约 32 ms。它没法在一般情况下增量缓存，因为后面一个强调标记会给已经折好的文字
重新上样式（正是 `commit` 扣住这类行的原因），所以这个测试固定一个天花板，
用来抓住退化成肉眼可见卡死的回归。

`tests/live_openrouter.rs` 里的
`live_streamed_reply_render_is_prefix_stable_at_real_chunk_boundaries` 和
`live_streaming_never_loses_or_repeats_a_row` 在真实 provider 的 chunk 切分上
证明了同样的不变量，而 `scripts/live_smoke.sh` 把构建出的二进制在 tmux 里过
一遍实时 torture 回复、流中途的 Esc，以及流中途的 resize。

### Scrollback 与条带共享同一条前沿

条带预览的**正是 `commit` 扣在 scrollback 之外的那些行**：`preview` 返回的是
`committed` 所索引的那同一个虚拟 `frozen ++ tail` 序列里未提交的尾部。这一条
共享的前沿就是全部契约 —— 在每一刻
`committed ++ preview == assistant_lines(prefix)`，所以回复始终完整地在屏幕
上，分布在 scrollback 和条带之间，没有东西被显示两次。

它必须是从前沿*推导*出来的，而不是在前沿旁边另挑。预览过去自己挑行 ——
「最后渲染出的那一行」—— 而两种与 `commit` 不一致的方式都触得到，因为 `commit`
是按**源码行**扣留的，不是按行：

- 一条被扣住的源码行若折成**好几**行，预览只显示它的最后一行，其余的直到该行
  定下来都干脆不在屏幕上。任何被 `commit` 整行扣住的行都这样：一行围栏代码
  （它在行结束前颜色未定）、一行带未闭合 `**`/`` ` ``/`[` 的文字、一段残缺
  围栏或标题序列。对着一条真实的 OpenRouter 回复实测，宽度 40 下的一个宽
  `vec![…]` 字面量丢了 **28 行** —— 文字随着该行生长肉眼可见地消失，然后一下
  子落下来。
- 一条被扣住、渲染成**零**行的源码 —— 一个闭合 ``` —— 让预览没有自己的行，
  旧的兜底逻辑就退回到最后一行 `frozen`，而它已经在 scrollback 里了。每个围栏
  块在闭合的那一刻都把它的最后一行代码画了两次。

`commit` 仍然扣住**最后一个非空行**
（`StreamRender::stable_keeping_preview_row`），而不是仅仅扣住生长中的末行，
所以一行刚完成时会留在预览里，直到更新的内容取代它才提交（**慢流重复行的
bug**：一个以 `\n` 结尾的 chunk 完成了一行，而在慢模型上，下一个 chunk 之前的
空档会让这个重复滞留）。

当前沿干净时 —— 渲染出的都提交了 —— 预览是**空的**，条带也不预留预览行，这
正是流开始前那次停顿的形状。所以 `ui::preview_rows` 原样报告注入的行数；在那里
设下限会预留一行 `preview_lines` 并不会画的行，从而触发它的 `debug_assert`。
**上限**是几何唯一会做的调整 —— `ui::preview_budget` 把这个槽位限制在该区域
剩余的行数上，而 `preview_lines` 把前沿裁到同一个数（从尾部先裁，所以最新的行
留下来），这才让一个很高的预览不会在小终端上把 composer 挤出去
（`docs/ui/table-streaming.md` *The preview slot is budgeted*）。

`ui::tests::preview_and_scrollback_together_show_the_whole_reply` 在覆盖每种
被扣结构的语料的每一个前缀上，按真实的流式顺序（先 commit，再是绘制的
preview）驱动一遍，并断言上面那个等式；
`preview_never_shows_a_committed_row_while_streaming` 钉住「不重复」那一半，
而 `a_wrapped_code_line_previews_every_row_not_just_its_last` /
`a_closing_fence_never_previews_an_already_committed_row` 按名字钉住这两处
回归。`live_streaming_never_loses_or_repeats_a_row`
（tests/live_openrouter.rs）在**真实** provider 的 chunk 边界上复核同一个等式。
