# token 估算，由 provider 校正

日期：2026-11-05

应用需要一些它还没拿到的 token 计数。回复流式输出时状态行的计数在跳，页脚的上下
文量表必须在下一次请求发出之前说出窗口有多满，自动压缩要据此决定是否在 90% 处
开跑，`/context` 页面把窗口拆成分项，Ctrl+D 给每条消息贴标签，而一次压缩要记下
它把上下文压到了多小。provider 每轮只报一次某个请求的真实大小，就在它的 usage
帧里（`StreamEvent::Usage`、`docs/providers/prompt-caching.md`）。其余的全都靠
估。

`src/tokens.rs` 就是整个答案，分成两半：

1. **`tokens::estimate`** 在任何 provider 看到一段文本之前算出它的 token 数。它
   不需要词表，也不偏向任何 provider。
2. **`tokens::ContextMeter`** 和 **`tokens::Calibration`** 把每一帧 usage 当作
   它就是的真话，并用它教给的东西校正同一段对话此后的每一个估算。

## 它替换了什么，为什么

应用以前用 OpenAI 的 `o200k_base` 字节对编码来数：tiktoken 的一个紧凑的
crate 内移植，1.6 MB 的词表嵌在二进制里，加载之后约 5 MB 常驻，切分模式要用
`fancy-regex`，启动时开一个线程在第一个回合需要之前把表建好，还要 `tiktoken-rs`
作 dev 依赖来证明它数出来的结果一样。

它是精确的，但大多数时候只是对**错误的分词器**精确。OpenAI 之外的每个 provider
都用自己的词表来数：Anthropic 的、Antigravity 上 Gemini 的、Ollama 或
LM Studio 上本地模型的、OpenRouter 目录里任何一个的。为一套词表买来的精确，对
其他那些什么都没换来。而差距恰恰在应用最依赖这个计数的地方最要紧：一次压缩、一
次回退、`/clear` 或 `/resume` 之后，量表退回裸计数，而裸计数既看不见 provider
的分词器，也看不见每个请求都携带的 tool schema。在两次 usage 帧之间，加进对话的
任何东西都不会让量表动一下，所以一次大粘贴或一段 tool 输出，要等到下一次请求被
数过之后才显现出来。

于是精确计数被换成了一个对每个 provider 都接近的估算。此后各 provider 自己的报告
再把这个估算拉到那个 provider 身上。

## 估算

这个应用对话的那些 provider 用十几种词表来分词 —— OpenAI 的、Anthropic 的、
Gemini 的 SentencePiece、Llama 的、Qwen 的、DeepSeek 的、Mistral 的 —— 而在英
语之外，它们相差两到三倍：测试里那段印地语样本对 `o200k_base` 是 28 个 token，
对 `cl100k_base` 是 100 个。没有哪个本地计数能对它们全都精确，所以这个估算不去
争取对某一个精确。它们对一段文本做的事大同小异，而 `estimate` 就把那个共同点建
成模型：一趟走过字符，热路径上一张 ASCII 表，每一片以千分之一个 token 计价，好让
小数精确累加、只有总数才取整，没有词表、没有正则、没有分配。

| 片段 | 估算 |
| --- | --- |
| 一个词（任何非 CJK 文字的字母） | 头六个字母算一个 token，之后每个字母四分之一个 token；在 `camelCase` 换大小写处切开，`HTMLParser` 在最后一个大写处切 |
| 一个全大写片段（`HTTP`、`MAX`） | 约六个字母一个 token，至少一个 |
| 一个带重音的拉丁字母 | 在它的词上再加 0.4 |
| 一个西里尔字母 | 0.3 |
| 一个希腊、亚美尼亚、格鲁吉亚、希伯来或阿拉伯字母 | 0.5 |
| 一个印度诸文字、泰文、老挝文、藏文、缅甸文、高棉文、埃塞俄比亚文的字母 | 0.55 |
| 一个汉字、假名或谚文音节 | 0.85 |
| 一个数字 | 每三位数一个 token |
| 词或标点前的一个空格 | 不算：它搭在那一片上 |
| 数字前的一个空格 | 1.5：没有哪个预分词器会把空格并到数字上 |
| 两个及以上的空格，或者结尾的空格 | 这一串算 1.3 |
| 一串换行（中间的空格也算进来） | 0.75 |
| 紧跟在标点之后的换行 | 不算：它并到标点上 |
| 一串标点 | 每五个字符一个 token，至少一个 |
| 开一个词的那一个标点字符 | 0.5；路径、URL 和标识符由之构成的那些算 0.15：`/ . _ - ' @ $ # ? & % \ < * ! + =` |
| 一个 emoji 或象形符号 | 2.2，每个连接符、变体选择符或肤色算 0.6 |
| 一段看起来随机的 base64 | 约每一点五个字符一个 token |
| 一个控制字符 | 1 |

一个词从不少于一整个 token，而非空的文本从不少于一个。base64 那条规则是这个估
算唯一往前看的地方：一段至少二十个字符长、大小写都有、其字母在三分之一以上的字
符处换大小写或者变成数字的 base64 字符表序列。词、路径和标识符在那段长度里只换
几次；base64 每隔一个字符就换，而且分词的密度是词的三倍：lockfile 里的完整性哈
希、日志里的一个 JWT、一个 tool 打印出来的 `data:` URL。没通过这个测试的序列按
词和数字来读，而且不再重测，这让这一趟保持线性。

### 它是怎么拟合出来的

这些代价是用坐标下降、然后取整，对着 tiktoken 的 `o200k_base`（GPT-4o 及之后）
和 `cl100k_base`（GPT-4，以及 Llama 3 与 Qwen 词表的形状），在 307 个约 3 KB 的
样本上拟合出来的：本仓库的 Rust、Markdown、JavaScript、Python、shell、TOML、
YAML 和 SQL；美化过和压过的 JSON；`git log --stat`、diff、`ls -la`、`ps`、
`find` 和 `grep` 的输出；日志、CSV、URL、UUID、十六进制摘要和 base64；十六种语
言的散文，以及一段满是 emoji 的聊天。目标是两个参照的几何平均，权重 0.65 偏向
`o200k_base`，因为多数 provider 现在服务的是更新、更密的词表。两者一致的地方
（英语、代码、数据、tool 输出），那个目标与两者都只差几个百分点；它们不一致的地
方，它落在两者之间。

### 有多接近

在一份它没被拟合过的 13 MB 文本上测量，共 3.7M 个 `o200k_base` token：198 个
crate 的 Rust、Python 标准库、C 头文件、JavaScript 和 TypeScript 声明、JSON、
TOML、shell 脚本、新鲜的命令输出，以及约三十种语言的两段文本（vim 教程和
*Alice* 的一章）：

| 内容 | ÷ `o200k_base` | ÷ `cl100k_base` | 每文件平均误差 |
| --- | --- | --- | --- |
| Rust / Python / C | 0.99 / 1.01 / 0.97 | 1.00 / 1.02 / 0.98 | 4–6% |
| JavaScript / TypeScript 声明 | 1.00 / 1.11 | 1.01 / 1.12 | 5% / 16% |
| Markdown / JSON / TOML | 0.97 / 0.94 / 0.96 | 0.97 / 0.94 / 0.96 | 4% / 9% / 4% |
| shell 脚本 / 命令输出 | 0.92 / 0.99 | 0.93 / 0.99 | 8% / 6% |
| 英文散文 | 1.08 | 1.00 | |
| 另外 21 种拉丁文字语言 | 0.89 | 0.79 | 11% |
| 俄语、乌克兰语、保加利亚语 | 0.98 | 0.68 | |
| 希腊语 / 阿拉伯语和希伯来语 / 泰语 | 1.14 / 1.11 / 1.15 | 0.55 / 0.52 / 0.58 | |
| 中文、日文、韩文 | 1.08 | 0.83 | |
| **全部** | **0.98** | **0.97** | |

一个词表像 `o200k_base` 的 provider，在 coding session 主要携带的东西上遇到的估
算只差几个百分点。一个对某种语言词表更薄的 provider，会把那种语言数得比估算更
高，而这正是下面的校准要学的东西。一旦某个 provider 报过数，水平就没那么重要
了，重要的是估算在各类文本上跟得有多*一致*，因为一个比例覆盖整段对话。上面几行
里，比例的取对数在 `o200k_base` 上离散度是 0.07（约 ±7%），在 `cl100k_base` 上
是 0.23。

测试在没有参照 crate 的情况下让这次拟合保持诚实。二十一个样本带着它们在代价被拟
合时的 `o200k_base` 和 `cl100k_base` 计数。每一个都必须落在加权中点的四分之一以
内，而英语、代码和 tool 输出那几个合计要在 `o200k_base` 的十分之一以内
（`every_sample_lands_within_a_quarter_of_the_reference_tokenizers`、
`english_code_and_tool_output_land_within_a_tenth_of_the_tokenizers`）。改一个
代价就是改拟合，而那两个测试会说它是否还站得住。

它在闲置时不花什么。没有表要建，也没有东西常驻，所以那个预热编码器的启动线程没有
了。它是一趟无分配的扫描，在上面那份语料上 release 构建里约 160 MB/s，而同一台
机器上 `tiktoken-rs` 的 `o200k_base` 是 17–19 MB/s。词大小的片段加起来恰好等于
它们整体的估算，所以那个边流边估每一片的 live 计数，和对整条回复的估算是一致
的。

## 校正

### 量表读的是什么

`ContextMeter` 以 provider 的 token 为单位，保存一段对话的上下文大小：

- **一帧 usage 设定基准。** 它的 `input` 是 provider 自己对请求整个上下文的计
  数，包括估算只能近似的东西：按 provider 渲染方式呈现的 tool schema、chat 模
  板的框定、provider 加的任何东西。量表把这个计数，和在同一帧取的、对同一份上
  下文的估算放在一起，而量表读的就是 `input`。这一帧报成 `output` 的回复在被记
  录之前不是上下文。在多数线上，它的 reasoning 永远不是，这就是量表不把
  `output` 加进去的原因：旧的 `input + output` 会高估推理模型的回合，直到下一次
  请求，还可能提前触发一次自动压缩。
- **帧之后加入的东西加的是它校正过的估算。** 回复、一个 tool 的输出、用户下一
  条发出的消息。循环的底部（`App::sync_context_used`，什么都没动时只花两次整数
  比较）只估算基准之后加入的那部分历史，且完全按一个请求会携带它的方式来推导。
  所以一次大粘贴或一段 tool 输出立刻显示在页脚上，在下一次请求被数之前。
- **在任何帧之前，估算就是读数，tool schema 也算在内。** 后端的 tool 集合
  （`ReplySource::tool_definitions`，每个 schema 按 client 序列化出来的样子）在
  每个循环底部交给 `App`，并和上下文的其余部分一起估算。所以一个 session 的第一
  个请求、一个恢复的 session，以及一个不报 usage 的 provider，都把每个请求都携
  带的 schema 算进去。tool 集合一变（一个 MCP 服务器连上、Tools 那个旋钮），就
  用新集合的估算重读整个上下文，而某一帧的基准里已经存着 provider 对旧集合的计
  数。
- **一帧不再描述的上下文会挪动基准。** 一次压缩、一次回退、`/clear` 之后又来一
  条新消息、或者一次 `/resume`，会把整个上下文重新估一次，并把这个读数按这次变
  化校正后的估算挪动。provider 数出来的超出估算的部分留着。这就是它对一次压缩
  意味着什么。最后一帧给一份估算为 84k 的上下文数了 88k，因为 provider 用自己的
  方式渲染 tool schema、框定消息。摘要留下估算 6k，schema 也在其中。量表，以及
  `● Context compacted · 88k → 10k tokens` 那个 cell，读的是 10k：provider 的
  计数减去摘要替换掉的 78k。它们以前读的是裸估算，压根不含 schema。
- **一段空的对话仍然读作真正的零**，一如它一贯的样子
  （`docs/architecture/compact.md`），不管 tool 是什么。
- **摘要器自己那一帧什么都量不到。** 一个 `/compact` 请求的形状和对话不同：没有
  tool，加上 compact 的 prompt。

### provider 教了什么

`Calibration` 学这个 provider 的 token 与估算相比是什么关系。一个样本是相邻两帧
之间的变化：provider 对加入上下文的那些东西的计数，对照对同一变化做的估算。两帧
都原样携带的东西（tool schema、system prompt、框定）约掉了。剩下的就是 provider
的分词器把这段 session 的文本按每个估算 token 变成多少个 token，比方说一个分词器
把代码切得比估算更碎的模型是 1.18。几道守卫把坏样本挡在外面：

- 一个不足 256 个估算 token 的变化被跳过，因为 chat 模板的逐消息框定对任何更小
  的东西都是一份真实的份额；
- 一个比例落在 0.4–2.5 之外的变化，量到的是别的东西（连上来的一个 tool 集合、
  一个变了的 system prompt），跳过；
- 在这期间来了一张或走了一张图片的变化被跳过，因为估算给图片记的是 256 个
  provider 并不共享的固定 token；
- 换模型（`App::set_session_info` 点名了另一个模型）会把校准重来，而新模型的第
  一帧不和旧模型的比；
- 比例是各样本之和除以各估算之和，所以大的变化比小的更重。估算累计超过 64k
  token 之后，旧的样本被减半掉，好让它跟随这个 session 现在在做的事。它被夹在
  0.5–2.0，也就是两个现代分词器之间最大的差距。

**为什么用帧之间的变化，而不是整个请求。** 整请求计数与它估算的比例从第一帧就存
在，但它把不是文本的东西也按文本那样缩放：provider 渲染得比它们的 JSON 更紧凑的
tool schema、一张 provider 收 1,500 个 token 而估算只记 256 的图片。拿同一批构造
出来的情形跑一遍，当 schema 的估算比 provider 的计数高 8k 时，整请求比例把一次压
缩的结果读高了 50–65%；在一张早期图片之后的那个请求读高了 40%。帧之间的变化把两
者都精确读了出来。代价是要等第二帧这个比例才存在；第一帧本来就已经是读数的基
准。

这个比例校正上下文的每一个估算：帧之后加入的东西、一次压缩或回退造成的变化、
`/context` 页面上的每一个计数，以及每一个 Ctrl+D 标签。于是页面上的总数和页脚
说的是同一批 token。两个视图都在各自 memo 之外施加它 —— memo 里存的是估算自己
的计数 —— 并且都把它算进缓存键，所以一条新学到的比例会触发重算而不用重新分
词。它**不**碰状态行的 live 计数，那个反正会被每一帧对齐到 provider 计费的总额
（`docs/providers/prompt-caching.md`），也不碰 `Thought for …` 那个 cell，它对齐
到 provider 的 `reasoning_tokens`（`docs/ui/thinking-stream.md`）。

一个 subagent 在 `AgentRun` 上保留自己的量表，往下移一层用同样的规则
（`docs/agents/agent-context-gauge.md`）。它在自己的各帧和每次落定时读，所以它
的 session 视图里的量表会把每个回合结束时的那条回复折进去。

## 限制

- 校准住在内存里。一个新 session 或恢复的 session 从 1.0 开始，从它的第二帧起
  开始学。
- 一张图片在估算里是固定的 256 个 token。provider 真正收的钱只经一帧的基准进
  来，从不经这个比例。
- 一个比例覆盖整段对话，所以一个混着 provider 数法差别很大的文本（先散文、后
  base64）的 session，是按平均来校正的。
- 一个 subagent 的估算不带 tool 集合，所以它的量表从它的第一帧起才数得到自己的
  tool schema。
- 重估整个上下文在循环的线程上每帧跑一次，每段文本的计数都记着上一次的结果：2
  MB 历史下不到 2 ms（第一次 3 ms），所以它留在那儿，而不是挪到后端的线程上。
- 帧与帧之间的量表仍然是估算，但只估最后一次帧之后加入的东西，那通常是窗口的一
  小份。
