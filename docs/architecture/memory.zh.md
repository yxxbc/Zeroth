# 常驻内存：应用持有什么，以及 `/model` 过去要花多少

Zeroth 是用户终端里一个长期存活的前台进程，所以它的常驻集本身就是一项
功能：它在回合之间空转，而它持有什么，就整个 session 都持有。启动是
**约 16 MB**。打开一次 `/model` 过去会把它带到 **25 MB** 并停在那里 ——
重复打开还会爬到 26 MB 以上 —— 因为 picker 的模型列表是用一种代价十倍于它所
读正文的方式解析的，而且一分都不还回来。

## 测量

两个探针，都用 `/proc/self/status`（与当年测出旧 `o200k_base` token 计数器
45.5 MB 的同一套方法，`docs/architecture/token-estimate.md` —— `VmRSS` 是
此刻常驻的量，`VmHWM` 是一次瞬时尖峰留下的峰值）：

- **`cargo run --release --example mem_probe [body.json]`** —— 一次
  `/v1/models` 解析让进程付出多少（不给抓包时会生成一个合成的 OpenRouter
  形状的正文，所以从一份干净的检出就能跑）。`--dom` 在一个独立的新进程里
  重新测量它所替代的整份正文 `serde_json::Value` 树，好在同一份正文上做
  同口径对比。设了 `OPENROUTER_API_KEY` 时，Part B 会跑真实的抓取。
- **`tests/model_parse_memory.rs`** —— 回归闸门，由普通的 `cargo test`
  运行。它住在一个自己的测试二进制里，因为这项读数是进程级的：一个孤零零的
  `#[test]` 旁边没有任何东西污染测量，而一个与库的 2800 个测试共用二进制的
  `#[cfg(test)]` 模块做不到这个承诺。在没有 `/proc` 的地方它会跳过（而不是
  对着噪声断言）。

下面那些端到端数字来自在 tmux 下用一个 OpenRouter key 驱动真实的二进制，并
采样进程的 `VmRSS`。

## 错在哪里

`llm::models::parse_models` 把响应反序列化成
`ModelsResponse { data: Vec<serde_json::Value> }` —— **每一条记录的每一个
字段**的完整树 —— 然后从每条里读出七个键：`id`、`name`、
`context_length`、`reasoning`、`supported_parameters`、`architecture`
和 `model_spec`。

OpenRouter 的实时列表量到 417 条记录、669 KB JSON。按字段称重（值字节加上
键/语法开销）：

| 字段 | 字节 | 读了吗？ |
|---|---|---|
| `benchmarks` | 153.7 KB | 没有 |
| `description` | 93.0 KB | 没有 |
| `supported_parameters` | 84.2 KB | 读了 |
| `architecture` | 67.9 KB | 读了 |
| `pricing` | 53.5 KB | 没有 |
| `top_provider` | 39.5 KB | 没有 |
| `default_parameters` | 35.4 KB | 没有 |
| `links` | 31.4 KB | 没有 |
| `reasoning` | 23.7 KB | 读了 |
| `canonical_slug` | 19.5 KB | 没有 |
| `name` + `id` + `context_length` | ~36 KB | 读了 |

大约三分之二的字节从未被读 —— 但读的那部分从来不是重点：一棵 `Value` 树
在读过的和没读的字段上一样付约 10 倍，因为每个字符串都是自己的堆上
`String`，每个对象都是一个 `IndexMap`（`preserve_order` 特性），每个数字
都是一个装箱的 enum。对着那 669 KB 正文，整表树量到常驻 **+6.5 MB**，而
picker 保留的那些行（`ModelEntry` —— id、provider、name、一个 effort 阶梯、
两个小选项）总共 **~47 KB**。

问题的另一半是：**把树丢掉什么都不还回来**。探针在 `drop` 前后读到同样的
RSS。这棵树是成千上万个小分配，交错撒在 arena 里，所以 glibc 的 `free`
几乎无法把它们中的任何一个合并成一段可归还的区间 —— 页面继续映射，进程继续
大着。这就是为什么一次 `/model` 打开是永久的 +8.7 MB 而不是一次尖峰，也是
为什么关掉 picker（它确实 drop 了那些行 —— `App::close_model_picker` 把
`model_picker = None`）什么也没改变。重复打开还会继续爬，因为每次抓取都跑在
一个新的 worker 线程上，可以落在另一个 glibc arena 上，各自长自己的池。

## 修法：一次只解码一条记录

信封现在把每条记录当作**未解析的 `serde_json::value::RawValue`** 持有 ——
一段借来的响应正文切片，不是堆上的副本：

```rust
struct ModelsResponse<'a> {
    #[serde(default, borrow)]
    data: Vec<&'a serde_json::value::RawValue>,
}
```

而 `parse_models` 通过逐记录的 `entry_of` 一次解码一条，在解下一条之前把
这一条的树丢掉。峰值现在是**一条记录的树**（~2 KB）加上 417 个胖指针
（~7 KB），而每条记录的分配直接还给下一条记录所复用的同一批块 —— 所以
arena 永远不会长到一次装下整张表。

那些嗅探函数（`reasoning_support_of`、`vision_support_of`、
`context_window_of`）仍然接一个 `&Value`：这是改变那个 `Value` 如何被
产生，而不是改变从它里面读出什么。一个数组的每一个元素只要能被解析为 JSON，
它自身就是合法的 JSON，所以逐记录的 `from_str` 在能走到这里来的正文上不可能
失败，而逐记录的跳过（一条畸形的聚合器行被丢弃，绝不致命）与旧行为逐字节
相同 —— 由 `entry_of_reads_one_record_and_skips_an_unusable_one` 及旁边的
宽容字段测试锁住。

## 它换来了什么

解析 OpenRouter 真实的 669 KB 列表：

| | RSS 增长 | drop 时归还 |
|---|---|---|
| 整份正文 `Value` 树（`--dom`） | **+6.5 MB** | 无 |
| 逐记录解码（`parse_models`） | **+0.4 MB** | 不适用 —— 它从未长过 |

那约 0.4 MB 主要是 picker 合理保留的 417 行 `ModelEntry`，加上一轮解析的
churn。

端到端，真实二进制对着 OpenRouter：

| | 之前 | 之后 |
|---|---|---|
| 启动 | 16.3 MB | 16.3 MB |
| 第一次 `/model` 之后 | 25.0 MB | **19.1 MB** |
| 稳态（三次打开） | 26.0 MB，还在爬 | **19.6 MB，平的** |

**省了约 6 MB**，而这个节省随扇出放大：`/model` 并行抓取**每一个**已配置
的 provider（`ModelSession::begin_model_fetch`），所以一个有三把 key 的用户
过去要付三棵并发的树，现在付三次约 0.4 MB 的解析。启动时的能力探测
（`ModelSession::resolve` 的 `probe`）在第一次绘制之前对 env 选中的模型跑
同样的解析，所以它也拿到同样的节省。

## `/model` 剩下的开销是什么，为什么它留着

第一次 `/model` 仍然要付的约 +2.9 MB 不是 JSON：

| | 开销 | 一次性？ |
|---|---|---|
| 第一个 `reqwest::blocking::Client`（runtime 线程、连接池、TLS 配置） | ~1.4 MB | 是 |
| 第一次真实的 HTTPS 交换（crypto provider 初始化、握手缓冲） | ~1 MB | 是 |
| 响应正文的那个 `String` | ~0.7 MB | 瞬时；单个大分配，所以它*确实*会还回来 |
| 保留的 `ModelEntry` 行 | ~0.05 MB | picker 开着时持有 |

client 和 TLS 的开销是*任何*一种第一次网络调用都要付的 —— 一个真实的 chat
回合也要付（实测：一个先 chat 的 session 落到的稳态同样是约 20 MB，而
`/model` 那时只再加约 0.5 MB）。它们不是 `/model` 该省的。

解析之外还有两道小护栏让抓取有界：

- **一个 client，不是两个。** `llm::http_client` 按每操作超时来缓存 client，
  而模型抓取过去传自己的 30 s 期限 —— 在 chat client 旁边建了第二个完整的
  client（自己的 blocking-runtime 线程、连接池和 TLS 配置），并在整个进程
  生命周期里持有它。它现在共用 `openai::NET_OP_TIMEOUT`，所以整个 session
  骑在一个 client 上。说实话：那个*边际* client 实测远低于约 200 KB（信任
  锚是静态的，crypto provider 初始化是进程全局的 —— 只有第一个 client 付那
  一兆），所以这里更多是少一个常驻线程、多一个共享连接池 —— `/model` 的抓取
  预热的正是下一个 chat 回合要复用的那条连接 —— 而不是一次内存胜利。
- **正文读取有上限**（`MODELS_BODY_MAX_BYTES`，8 MiB —— 即
  `SHELL_OUTPUT_MAX_BYTES` 的姿态）：一个坏掉或敌意的端点无法用一个无界的
  `read_to_string` 把 worker 撑爆；在上限处被切掉的正文解析失败，报成一次
  普通的解码错误。

## 测过而刻意不改的

**`ModelPicker::matches` 会分配** —— 每次调用一个 `Vec<&ModelEntry>`，并且
每敲一个键就把每个 id/provider/name 转小写，且每次渲染有好几个调用点。往一个
417 个模型的 picker 里打字，RSS 动过一次约 0.05 MB，之后再多的按键都纹丝不
动：这些分配是均匀的、短命的、立刻被复用的。那是 CPU churn，不是内存问题，
而这份文档讲的是内存。

## 内联图片付同样的租金

一次 kitty placement 把整幅图作为 base64 RGBA 持有 —— 一张在 10x20 单元格
下 120 列的截图是 1200x600 像素，约 2.9 MB 像素、约 3.8 MB base64 —— 所以
编码图存储按**字节**而不是按条目设上限（`docs/ui/images.md`）。预算是按
placement 自己的几何来扣的，不是按编码器内部，超过 24 MB 就淘汰最久没被绘制
的那幅图；再次满足同一个需求只会花一次重新编码，绝不是一幅错的图。

面向模型的缩放反过来有界：解码常驻的是 `4 x width x height` 字节，所以它
超过 5000 万像素（或 64 MB 源）就直接拒绝，调用方宁可拒绝这次读取，也不会
真的去物化一张 12000x12000 的扫描、然后才发现不该这么做。

## 粘贴一张截图：卡住的那个往返

报告说的是「每次 Ctrl+V 粘贴一张图，进程就变大，超过 100 MB」。在一个虚拟 X
服务器下复现 —— `Xvfb :99`，`clipboard_owner` 示例提供一张 1920x1080 截图
形状的 PNG（带逐像素噪声的渐变，所以压缩起来像真的），二进制跑在 tmux 里，
每步之后采样 `VmRSS` 和 `VmHWM`：

| 只粘贴，五次 | RSS | 峰值 |
|---|---|---|
| 启动 | 18.0 MB | 18.0 MB |
| 粘贴 1 | 24.3 MB | 42.5 MB |
| 粘贴 2 … 5 | 19.0 MB | 42.8 MB |

| 粘贴 + 发送，三次 | 粘贴之后 | 发送之后 |
|---|---|---|
| 图 1 | 24.1 MB | 41.2 MB |
| 图 2 | 59.9 MB | 78.9 MB |
| 图 3 | 103.1 MB | 103.3 MB |

（half-block；在 kitty 下同一轮达到 **122.5 MB**。）单是粘贴是一次 24 MB
的尖峰，大部分都回来了。*发送*那幅图才是卡住的部分，一次约 20 MB，而且再也
不回来。

### 三笔开销，以及它们为什么复利

**粘贴把手上已经编码过的字节解码又重编码了一遍。** 在 Linux 上，截图工具把
它的图作为 PNG 放到剪贴板上，而 `image/png` 正是 arboard 向所有者索取的唯一
目标 —— 之后它把它解码成 RGBA、把像素交过来，而 `read_clipboard_image` 又
把它们 PNG 编码回磁盘。对 1920x1080 来说那是一个 8.3 MB 的 RGBA 缓冲、
一个编码器的工作集，以及一个一路翻倍长过 8 MiB 的输出 `Vec`，全都为了复制
所有者本来给的字节。

**显示为了画一幅小图把整幅图解码。** 提交 user 气泡时会画它下面那幅图
（`docs/ui/images.md`），而 `ImageStore::encode` 把整张 PNG 解码 —— 又是
`4 x width x height` —— 才缩到约 118 列的块，也就是约 3 MB。

**glibc 留下了第二个。** `malloc` 会用一块私有映射服务一个超过它 `mmap`
阈值的块，而 `free` 确实会归还那种块 —— 但阈值是*动态*的：释放这样一个块会
把阈值提到该块的大小（上限 32 MiB），于是*下一个*同样大小的块就从堆里切，
而在堆上，一次不在最顶端的释放什么都不还回操作系统。粘贴那个 8 MiB 的输出
向量把阈值抬过了 RGBA 的大小，从那以后每一次整图解码 —— 渲染的、重发的 ——
都落在堆里并且留下。这就是每次发送 +20 MB，也是它看起来像泄漏的原因。

### 改了什么

- **粘贴改为流式处理 PNG。** `clipboard::linux` 自己向所有者索要
  `image/png`，并在字节到达时把它们拷进粘贴目录：一个 Wayland offer 是一条
  管道，一个 X11 selection 每次抓一个 1 MiB 的属性切片，包含 `INCR` 分段。
  不解码、不编码，手上永远不超过约一兆 —— 而一张 4K 截图，arboard 在 X11
  上根本读不了的那种（它自己所有者侧的传输会超过服务器的请求上限），与小图
  占用同样的内存粘进来。直接读取搞不定的，落回 arboard 的路径，而那条路径
  现在直接编码进文件，而不是经由一个不断长的向量。
- **PNG 按它将被显示或发送的尺寸解码。** `images::fitted` 把文件的行流过一个
  区域平均缩小，只物化目标尺寸：显示用的预留块（120 列下约 3 MB），模型用的
  2000 像素上限。峰值不再随截图放大 —— 一张 4K 的代价与一张 1080p 的一样。
- **`data:` URL 是一个分配** —— base64 追加在它的前缀之后，而不是先编码进
  一个字符串、再从后面拷进来。
- **载荷每个 session 缩一次，不是每个回合缩一次。** 一个附件在之后的每一个
  回合都要随 context 重发，而每个回合过去都会把它再解码再缩小一遍 —— 在
  一张 4K 截图上，只要图还在 context 里，每回合就是一次 20 MB 的尖峰。
  `images::payload` 把缩小后的字节留在磁盘上（`{session}/images/{key}`，以
  文件的路径、大小、mtime 和上限为键；`docs/tools/scratchpad.md`），而
  `cached_downscale` 在原件甚至还没被打开之前，就用那个小文件服务之后的
  回合。`read` tool 的图片走同一个缓存。这个目录封顶在
  `PAYLOAD_CACHE_MAX_BYTES`（64 MiB）：在新副本落地之前，`cache_eviction`
  点出最旧的 sidecar 该丢掉，好让它装得下。一个大于整个上限的副本会清空
  缓存，并且仍然被写入 —— 上限界定的是*保留*什么，而拒绝缓存一张大图，就会
  恢复这个机制存在的目的所要消除的逐回合解码。
- **其他任何东西都不会不问一声就整份解码。** 一张非 PNG 的图（粘贴的 JPEG
  照片、`read` 一张这样的图）只有在 `WHOLE_DECODE_MAX_PIXELS`（5000 万像素）
  之下才整份解码，并且用 `thumbnail_exact` 缩小 —— 一个没有 `f32` 工作副本
  的盒式滤波器，而 `resize` 会在源宽度上按每像素 16 字节分配。流式的 PNG
  解码在*时间*上由 `FIT_MAX_SOURCE_PIXELS`（2 亿像素）约束，因为它从不持有
  它走过的那些行。

### 它换来了什么

同样的流程，同样的图：

| 只粘贴，五次 | RSS | 峰值 |
|---|---|---|
| 启动 | 18.0 MB | 18.0 MB |
| 粘贴 1 … 5 | **19.1 MB** | **19.1 MB** |

| 粘贴 + 发送，三次 | 粘贴之后 | 发送之后 |
|---|---|---|
| 图 1 | 19.1 MB | 24.1 MB |
| 图 2 | 24.1 MB | 28.8 MB |
| 图 3 | 29.4 MB | **29.5 MB** |

一张 3840x2160 的截图：粘贴之后 18.8 MB，三次发送之后 28.8 MB —— 同样的
数字，因为这条路径上已经没有东西再按文件大小计量了。kitty 在三次之后落在
36.9 MB，它每屏的 placement 是 `docs/ui/images.md` 交代过的诚实的代价。
每次发送剩下的是那张缩小后的图以及由它构建的协议，几兆字节，阈值那套舞蹈
仍可能每个尺寸档留一次 —— 有界，而且小。

实测，对着 Venice 上一个真实的 vision 模型：一次 1080p 粘贴，粘贴之后读到
22.9 MB，答案之后 25.3 MB，中间那 54 MB 的峰值就是请求正文本身（文件、它的
base64、JSON），并且会回来。一张 4K 粘贴在**两个**回合上发送，就是载荷缓存
显形的地方：第一个回合在建 2000 像素载荷时峰值 63 MB；第二个回合过去会再解码
再缩小一遍、把峰值推到 85 MB，现在读缓存副本，峰值一点不动。

那些护栏：`tests/clipboard_linux.rs` 对着一个真实的 X 服务器驱动读取，覆盖
两种传输形状（一整个属性，以及 `INCR` 分段），并要求保存下来的文件*逐字*
持有所有者的字节 —— 以一个非默认压缩级别提供、并带一个 text chunk，任何
解码再重编码都复现不了 —— 外加一个只有 JPEG 的所有者；`images::tests` 把
缩小解码器钉在一个朴素的区域平均 oracle 上，把它的单元格算术钉在编码器自己
的算术上，并把载荷缓存钉在一次写入多次读回的语义上；而
`tests/image_paste_memory.rs` 为流式拷贝、缩小解码和 2560x1440 截图的载荷
缩小把关常驻增长，方式正如 `tests/model_parse_memory.rs` 为 `/model` 解析
把关 —— 流式拷贝在 2 MB 以下，另两个在它们自己的输出加上几兆字节余量之下，
全都比源那 15 MB RGBA 低一个数量级。端到端数字的流程是
`scripts/paste_mem.sh`（`docs/input/image-paste.md`，*Measuring*）。

## 每个回合都在重发那张图

粘贴修好之后的报告是那张图的*余生*：「我每发一条新消息 RAM 就涨」，一张
截图粘一次，画在对话里。用 `scripts/turn_mem.sh` 复现 —— 与上面同一套
harness，一次粘贴、一次发送，然后是每轮都把图随 context 重发的纯文本追问
—— 对着 Venice 上一个真实的 vision 模型，一张 1920x1200 截图形状的 PNG，
6.3 MB：

| 之前，halfblocks | RSS | 峰值 |
|---|---|---|
| 启动 | 22.0 MB | 22.0 MB |
| 发送之后 | 25.7 MB | 58.1 MB |
| 追问 1 | **39.3 MB** | 63.1 MB |
| 追问 2–6 | 39.3 MB | 63.2 MB |
| 追问 7 | **53.2 MB** | 77.0 MB |
| 追问 8 | 53.2 MB | 77.0 MB |

| 之前，kitty | RSS | 峰值 |
|---|---|---|
| 发送之后 | 29.1 MB | 60.5 MB |
| 追问 1 | **42.7 MB** | 66.4 MB |
| 追问 2 | **56.5 MB** | 80.2 MB |
| 追问 3–6 | 56.6 MB | 80.2 MB |

不是每条消息，而是每隔几条一个 **~14 MB** 的台阶，而且从不回落 —— 在一个
session 里无上限地长。那个台阶就是那幅图：6 MB 文件加 8 MB base64。

### 一个回合对一幅图做了什么

对话在每一个请求上整份重发（`docs/architecture/context.md`），所以附件搭上
之后每一个回合，而那些回合 —— 以及其中每一个 agentic 轮 —— 都在一个新的
backend 线程上从头重建它：

1. `image_data_url` **整份读文件**（6 MB）并把它 base64 编码进一个新字符串
   （8 MB）；载荷缓存只帮得上被自动缩放*缩小过*的图，而这张本来就已在 2000
   像素上限之内；
2. 为那一轮**克隆**消息（`messages.to_vec()` 进 `stream_chat`）—— 那份 8 MB
   字符串的一次深拷贝；
3. `build_payload` 建出整个请求的 `serde_json::Value` **树** —— 字符串又一次
   被拷进一个 `Value::String`；
4. `reqwest` 的 `.json()` 把树序列化进一个**靠翻倍**增长的 `Vec`，对一个
   8.4 MB 的正文最后到 16 MB 的容量，增长每一步都在背后释放一次拷贝；
5. 正文交给传输线程，在那里被释放。

一轮五个图片大小的块，约 46 MB 的瞬时流量，而 —— 让它*留住*的那部分 ——
没有一个是 mmap 来的。glibc 的动态 `mmap` 阈值早已被更早的一次释放抬过了
8 MB（*粘贴一张截图*所描述的同一个机制），所以那些块每一个都是从**线程
arena 的堆**里切出来的：`strace` 显示那个回合的线程把它的 arena 正好长了
6,172,672 字节、然后又 8,404,992 字节（`mprotect`），而什么都没有还回去 ——
堆只能从顶部收缩，trim 阈值是 mmap 阈值的两倍，而随后那些长命的小分配把
它们下面的东西钉住。每个 backend 线程从 glibc 的空闲表里拿一个 arena；当
那张表恰好空着时（一个传输线程、一个 tool、一个同时活着的粘贴 worker），
这个回合就落在一个**新** arena 上，并把一幅图的分量留在里面。那就是那个台阶，
也是它为什么每隔几条消息来一次而不是每条都来。

`examples/image_turn_probe.rs` 不经过网络重放这条请求路径（每线程一个回合，
正文像传输那样交给第二个线程），复现出同样的形状：第二个回合之后常驻 +8 MB、
一次 46 MB 的峰值、之后就平了。在 `MALLOC_MMAP_THRESHOLD_=65536` 之下跑 ——
固定阈值，没有动态抬高 —— 残留消失，峰值降 14 MB，这就是分配器在确认这个
诊断。修法不可能是那个旋钮（它是 `unsafe` 后面的一个 `mallopt`，而且会给
进程里每一个小分配加税）；而是不要再每个回合都申请图片大小的块。

### 改了什么

- **一个附件每个 session 编码一次并被共享。** `images::attachment` 把每幅图
  的 `data:` URL 按它的路径保存，用 [`AttachmentStamp`] 校验 —— 文件的大小
  与 mtime 加上 **Auto-resize images** 设置，也就是决定上传的是什么的一切 ——
  并把同一个字符串按引用交给每一个请求：`AttachmentUrl` 是一个 `Arc`，所以
  该回合那份消息的副本，以及一个显式缓存模型所用的标记副本，都是浅的。那
  唯一一次编码是**流式**写进它的字符串的，来源是文件或载荷 sidecar
  （`base64_encode_reader`，一个 48 KB 缓冲），所以构建它花的恰好就是它保留
  的；原件只在缩小它时被整份读一次。`read` tool 把它已经有的载荷交给同一个
  缓存（`remember_attachment`）。上限是 `ATTACHMENT_CACHE_MAX_BYTES`
  （32 MB，最久未发送的先出），并在每个回合开始时清扫到 context 仍携带的那些
  图（`retain_attachments`；一次 `/clear` 会清空它），好让一张被回溯或被
  压缩掉的图把它那几兆字节放掉。
- **消息的树，永远没有 —— 在任何线上。** Chat 请求是 `ChatRequest`，消息
  **按引用**放在一个小小的一览表旁边，而 prompt 缓存的断点标记一个浅的类型化
  副本（`cache::apply_cache_breakpoints` 作用于 `ChatMessage`，
  `docs/providers/prompt-caching.md`），而不是重写一棵 JSON 树。三条翻译过
  的线上格式 —— Anthropic 的 Messages API、OpenAI 的 Responses API、Ollama
  的 `/api/chat` —— 也建类型化请求，每个块、每个 item、每条消息都从对话里
  **借**，所以一个 image 块的 base64 是共享编码的一片切片，而不是它的一个
  `Value::String` 副本（每个模块的
  `the_request_borrows_a_pictures_bytes_rather_than_copying_them` 钉住那个
  指针）。`build_payload` —— 那棵树 —— 现在是测试对每一条线上请求的视图，
  而不是任何线上格式所构建的东西。
- **正文从不整份持有。** `llm::body::streamed_request` 把每条线上格式的请求
  当作一个 `BodySource` —— 会写出它自己那种类型化的、借用形式的数据 ——
  并在它自己的线程上把它序列化进一条 64 KB 块的有界管道
  （`BODY_CHUNK_BYTES`，四块深），传输层边上传边泵，`Content-Length` 来自
  一次什么都不分配的计数遍历。一个中间版本序列化进一个**恰好一次**定好大小
  的缓冲，仍然每隔几个回合就量到一次正文大小的台阶（+7.5 MB）：一个 8.4 MB
  的正文，比上一个只大几个字节，就落在上一个释放后留下的页取整阈值之下，于是
  像其他一切一样从 arena 里切出来。不让每个 arena 留一份正文分量的唯一办法，
  就是不构建这个正文。

## 流式 `write` 单元格保留了每一行的颜色

实时 `Write` 单元格（`docs/ui/write-streaming.md`）在模型写文件时给它上色，而
它的缓存保留了它**每一行**高亮过的分段：每个 token 一个 `String` 和一个样式，
约是该行文本的五十倍。用一个全局分配器在真实的 `App` 与 live 区域渲染器上
计量，一次 write 流式写入期间预览就持有这么多：

| 文件 | 之前 | 之后 |
| --- | --- | --- |
| 300 行，14.5 KB | 281 KB | 35 KB |
| 800 行，39 KB | 761 KB | 83 KB |
| 2,000 行，99 KB | 1,859 KB | 147 KB |
| 5,000 行，251 KB | 4,656 KB | 275 KB |

这些在回合结束时全都释放了，所以没有泄漏。但 glibc 会把进程用过的留下，所以
一个 session 预览过的最大的那个文件就永久定了它的尺寸。这是端到端量出来的：
引入预览之前那个提交（`317316a`）、预览刚合入时（`f77d92d`）以及修复之后
的三个 release 构建，在 tmux 下驱动一个替身 provider。每个回合之后的读数是
进程的**私有**内存，即它的堆加上来自 `/proc/PID/smaps` 的匿名映射，两次运行
取均值。`VmRSS` 的其余部分是二进制自己的文件支撑页，在刚构建的二进制和一个
稍旧的二进制之间能差上一兆，与代码做什么无关：

| 之后 | 没有预览 | 保留每一行 | 只留首尾最新 |
| --- | --- | --- | --- |
| 一次 300 行 write，第 4 回合 | 10.2 MB | 10.4 MB | 10.2 MB |
| 一次 2,000 行 write，第 1 回合 | 9.0 MB | 11.3 MB | 9.3 MB |
| 一次 2,000 行 write，第 4 回合 | 12.7 MB | 15.3 MB | 12.7 MB |
| 一轮里三次 800 行 write，第 3 回合 | 15.9 MB | 18.0 MB | 16.2 MB |

每回合的增长在三种情况里相同，因为那份增长是对话自己的历史（每次已提交
write 的单元格、参数和 transcript 行），它早于这个预览。

**修法**在于保留单元格*能显示*的，而不是它*见过*的。每一行仍然按顺序高亮
一次，因为语法的状态必须穿过中间才能给最新的那一行上色。但 strip 的缓存
`LineCache::windowed` 只保留最新十行和最早十行的分段，而那正是单元格的头和尾
所能显示的全部。只有当某个要显示每一行的视图（Ctrl+O 或 `/export`）索要时，
整个文件才被着色进第二个缓存。这样一来留下的就是解码后的文件加约二十行。
`tests/write_preview_memory.rs` 把一次流式 5,000 行 write 的常驻增长卡在文件
的四份拷贝上。它量到的是一份，而旧缓存的常驻代价约为二十七份。

## 代码生成 transcript 与改写 diff

在一次任务管理器生成回放中，被保留的 Ctrl+O transcript 是发现的最大一块可避免
的、持续增长的显示分配。每一个已提交的 tool 结果都被预渲染成展开的 ratatui
行：每个语法片段各持一个字符串和一个完整样式，哪怕 overlay 是关着的。保留这
个热缓存对快速打开是必要的（`docs/ui/tool-view-performance.md`）。

现在缓存保留一整块 UTF-8 文本、一张驻留样式表和编码后的分段长度/索引。
分页器只为它可见的那些行借文本。它仍然把每个已提交条目高亮一次、保留每一条
已记录的行、保持行对齐与图片/链接载体，并在不重新高亮的前提下重绘回溯选区。
完整的自有行仍可供显式调用者使用，包括 export；普通的分页器绘制从不构建它们。

刷新实时尾部现在会递减被移除行和分段所持有的样式引用，然后释放未使用的尾部
样式。这防止唯一的链接/图片载体在每次刷新时累积。选区变化也会平衡那些引用。
保留的分段 id 与缓冲区容量策略保持不变；未使用的中间槽位留到后面的样式被释放
时才动。在修复前，一个先失败的 churn 测试在 1,999 次刷新后留下 3,998 个陈旧
样式，修复后一个都没有。Unicode、空分段和多字节样式 id 都能往返通过截断与
追加。

在 `tests/transcript_memory.rs` 中，预热十二次 800 行的 TypeScript write
让常驻内存 **从 11.2 MB 变成 2.1 MB**。这包含了应用既有的带编号输出上限，
本次改动原样保留它。这个回归测试先在旧表示上失败，然后在紧凑表示上通过。
往返测试保住每一条分段/行的性质，缓冲区对比则覆盖主题、Unicode、短而窄的
终端、滚动与回溯。

改写路径还有另一块相当大的临时分配：`llm::tools::diff_lines` 每条旧行都在
一个向量里填上最多一百万个 `usize` 的 LCS 分数，在 64 位系统上约 **8 MB**。
匹配预算意味着一个分数至多是 1,000，所以一张扁平的 `u16` 表能装下同样的分数，
最多 **2 MB**，零边界是隐含的。空的中间段不分配任何表。前缀/后缀裁剪、平局时
的删除选择、计数以及既有的大 diff fallback 都未改变。一个穷举的小输入 oracle
和一个满预算的匹配测试把精确的 `DiffLine` 输出与原算法对比。孤立的峰值回归量
到 **从 8.5 MB 变成 2.1 MB**，并要求一个满预算大小的 diff 保持在 4 MiB 以下。

### 在请求快照之间共享生成的参数

一次 `write` tool call 的 JSON 参数里含有完整的生成文件。为一个请求轮、被保留
的线上前缀或 prompt 缓存标记而克隆对话，过去每次都要拷贝那份源码。
`llm::ToolArguments` 现在持有一个不可变的 `Arc<String>`：移动一个自有字符串
保住它的缓冲，而克隆一条消息就是共享它。序列化保住原始 JSON 文本，包括空白与
转义的写法。被保留的线上前缀预算按字符串的容量与共享分配的元数据计费，所以
一个缓冲过大而参数很短的字符串无法绕过既有的 8 MiB 上限。

`tests/tool_arguments_memory.rs` 在一个隔离的进程里让一次 6 MiB write 的四份
快照保持存活。这个测试先以 **24.0 MiB** 的额外 RSS 失败，然后在 **0 字节**的
计量增长下通过。单元测试检查共享分配的身份、精确的序列化字节与线上前缀复用。
这就是在那个受控案例里被消除的重复；整进程 RSS 还取决于渲染与分配器的复用。

对库的调用者来说，`FunctionCall.arguments` 现在是 `ToolArguments` 而不是
`String`。`ToolCallSpec::function` 接受与从前相同的输入。手写字段初始化可以用
`arguments: source.into()`；通过 `as_str()` 读取，或用 `to_string()` 产出一个
独立的字符串。

这两处新增有选择地从 `perf/reduce-post-generation-ram`（`342bac9`）移植了
有用的改动：共享参数与样式引用清理。紧凑的 varint 行、借用的 viewport 渲染、
隐式边框 diff 表和既有的缓冲区增长都保持原样。

### 不用模型 key 重放真实的 CLI 工作负载

构建一个 release 二进制，然后运行：

```sh
python3 scripts/codegen_mem.py target/release/zeroth --lines 5000 --turns 4
```

这个 Linux/tmux harness 启动一个隔离的 loopback Chat Completions provider，
它把 TSX、CSS 和 JSON 写入以碎片流式送出，然后驱动真实的二进制经历反复的生成
回合。它逐字节校验每个生成的文件、打开 Ctrl+O 与 Ctrl+D、两个方向都 resize，
并清空对话。`--output work/codegen.json` 保存 RSS、匿名/文件型常驻内存以及
采样的高水位读数。不启动任何生成出来的应用。fixture 里关掉了自动压缩，以保住
整个压力历史；应用正常的默认值不变。

干净的 `main`（`e98680d`，v0.15.0）与最初的紧凑缓存/diff 改动（`774ff7c`）
在 Linux x86_64 + glibc 上的匹配 release 构建，四个生成回合之后：

| 每回合 TSX 行数，外加 CSS/JSON | 之前 RSS | 之后 RSS | 降幅 |
| --- | --- | --- | --- |
| 800 | 38.85 MiB | 35.17 MiB | 9.5% |
| 2,000 | 44.76 MiB | 40.46 MiB | 9.6% |
| 5,000，两次运行均值 | 57.40 MiB | 52.00 MiB | 9.4% |

对 5,000 行那个案例，打开 Ctrl+D 之后的均值是 **从 64.04 变成 53.78 MiB**
（少 16.0%）；`/clear` 之后是 **从 58.15 变成 47.34 MiB**（少 18.6%）。
八次运行都校验了生成的文件、请求次数、两个 overlay、resize 和清空。最终的
Ctrl+O 打开观测在 7–33 ms 之内，包含 tmux 命令/捕获的开销。分配器在不同运行
之间有波动：两次基线大工作负载在生成之后的读数是 60.53 和 54.26 MiB，而改动
之后是 50.98 和 53.02 MiB。这些均值是这几次试验之间的对比，不是对每个 session
的保证。保存的 JSON 包含二进制的 SHA-256，好让以后的对比能确定是哪一个可执行
文件。

随后那次有选择的共享参数/样式清理跟进，是单独对着 `774ff7c` 量的，那时最初那
批改进已经在了。两个构建用同一个 v0.15.0 底。每个构建每个工作负载两次试验给出：

| 被保留的 RSS，两次运行均值 | 跟进之前 | 合并之后 | 降幅 |
| --- | --- | --- | --- |
| 5,000 行 TSX 加 CSS/JSON，四回合 | 58.23 MiB | 49.34 MiB | 15.3% |
| 13 文件的稠密生成，四回合 | 59.89 MiB | 52.44 MiB | 12.4% |
| 导出之后的稠密生成 | 61.94 MiB | 55.35 MiB | 10.6% |
| 清空之后的稠密生成 | 59.87 MiB | 53.28 MiB | 11.0% |

那个稠密 fixture 是 `342bac9` 的 `scripts/task_mem.py`，每回合 600 行、八个
组件、563,299 生成字节。它的峰值 RSS 均值从 103.57 降到 96.47 MiB。八次运行
都校验了生成文件字节、overlay、resize 与清空；稠密的那几次还核对了逐字的 tool
context 和 transcript 导出。一个 `codegen_mem.py` 的 scratch 扩展还在每个请求
里核对了此前所有生成路径与内容。导出所保留的增量在两个构建上都保持在 0.55 到
3.65 MiB 之间。

大 TSX 那一组的读数从之前的 52.64–63.82 MiB 降到合并后的 47.71–50.96 MiB。
这些试验在被测工作负载上显示出额外的节省，同时也带有上面描述的那种分配器
波动；它们并不预测一个实时模型的任务管理器实现的精确 RSS。

这是对分配路径的一次确定性重放，不是某个具体实时模型的输出。语法数据库和
HTTP/TLS 状态这类固定开销仍在，而原始对话历史仍随工作被记录而增长。单个条目
的临时展开行以及分配器保留的页面也会影响 RSS，所以降幅随 session 而变。

## 那条规则

这个模式可以推广到这一个函数之外：**不要为一份你只打算读出七个字段的正文建一
棵树。** 一个响应又大又大多被忽略时，把记录当作 `RawValue` 持有、一次解码一条。
做错的代价不是一次尖峰 —— glibc 不会把页面还回来，所以那是对一个用户整天开着
的进程的永久增量。`src/llm/models.rs` 是这棵树里唯一这样解析大型外部列表的
地方；其他那些 `Vec<Value>`（`llm::tools` 的 tool spec、MCP manager 的 tool
spec）都是应用所*发送*的小而固定的 schema。

同一条规则对图片还穿着一件外套：**绝不为做一幅小图而整份解码一幅图，也绝不
解码别人已经编码给你的东西。** 一张截图是这个进程所见过的最大的单次分配，而
分配器的动态阈值会把第二个这样大小的分配合永久化。`images::fitted` 流行式
处理；`clipboard::linux` 字节流式处理。

对请求还有第三条：**绝不为每个回合分配任何图片大小的东西。** 一个附件编码一次
并被共享（`images::attachment`），请求在每一条线上格式上都按引用从消息序列化，
而正文经由一条小块管道离开进程，而不是作为一个缓冲区
（`llm::body::streamed_request`）。那么大的一个块，又是在新线程上每个回合都要，
迟早会被 glibc 留在某个 arena 里。

而对任何边流边渲染的东西还有第四条：**保留视图能显示的，而不是它见过的一切。**
一个按输入而不是按窗口定尺寸的缓存，就是一个按这个 session 见过的最大的输入
定尺寸的缓存，而且要一直持续到 session 结束。
